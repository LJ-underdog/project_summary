1  M6b 是什么：三件事

M6 把 deterministic dQ 做到了 no_group（batched + jagged）。M6b 把它补齐到 group，并清掉 M6 文档里诚实标注的遗留缺陷 O1。验收过程中又顺手挖出一个与 determ 无关、但真能让 dQ 错的 harness 老洞。

事项内容性质
① group determM4/M5b group 结构 × M6 determ 机制：两个 group kernel（SiLU + softmax）dq_acc 窗口加 set+split 分叉，group dispatch 加 launch_main_and_post（num_splits / memset×num_splits / MAIN / reduce-or-convert POST），POST reduce kernel 直接复用 M6 的（mode-agnostic）。复用 M6
② 修 O1group entry BOOL_SWITCH_2 → BOOL_SWITCH_3 接 param.kIsDeterministic 真轴；group dispatch 去掉那条永不可达的 determ throw。group 是直接实例化（无 extern-template instance 文件），故无需改 generate_instances.py。修缺陷
③ 修 harness 老洞验收 1-FAIL 根因 = bwd harness group_max_seqlens_q 低估。改组内逐 batch 真最大 + HSTU_CHECK 守卫 + PRE 前置条件注释。库 kernel / dispatch / reference / fwd 一字未动。harness
determinism 自此覆盖全模式。 no_group（batched + jagged）由 M6 覆盖；group 由 M6b 覆盖；两者都跨 SiLU + softmax。M6b 后，「同输入跑两次得到逐位相同的 dQ」在所有已支持模式上都是构造保证（不再有 group 的静默 atomic 缺口）。改了 5 个文件、+186 / −114 行。

2  group determ 机制：照搬 M6 的 set + split + 固定序 reduce

dQ 是反向里唯一需要跨 KV-block 累加的梯度（每个 KV-block 都对全体 Q 行有贡献），所以 dQ 才有 determinism 问题（dK/dV 各自只在自己 block 内累加，无此问题）。group 路一样如此，机制与 M6 逐字相同：atomic 路 N 个 block 竞争 atomic_add 进一份 dq_acc（顺序不定）；determ 路每 block set（plain store，无 atomic）写进自己的 split 副本，POST 按固定升序归约。

图1：group deterministic 路 = M6 机制原样落到 group。每 KV-block set 写进专属 split 副本（base += i_tile_n·split_stride_dq_acc），POST 固定升序 Σ_s 归约（直接复用 M6 的 hstu_bwd_reduce_convert_dq_kernel，mode-agnostic）。下排为 M6b 在 group 路的全部三处改动。

① 两个 group kernel：dq_acc 窗口编译期分叉

hstu_attention_bwd_kernel.hpp · group SiLU kernel（HstuAttentionBwdDQDKDVGroupKernel）L1173-1181（group softmax kernel ...GroupSoftmaxKernel L1545-1553 同构） // M6b group determ: 与 M6 no_group 逐字相同的 mop 分叉 + split 偏移 constexpr auto mop = kIsDeterministic ? memory_operation_enum::set : memory_operation_enum::atomic_add; auto* dq_acc_ptr = ...; if constexpr(kIsDeterministic) dq_acc_ptr += static_cast<long_index_t>(i_tile_n_) * kargs.split_stride_dq_acc; // 本 KV-block 专属 split
params 只加两个字段。 HstuAttentionGroupBwdParams += split_stride_dq_acc / num_splits（hstu_attention_bwd_params.hpp），其余与 M4/M5b group 参数共用。kernel 的 mop 与 pipeline 早有的 if constexpr(kIsDeterministic) store_tile else update_tile 严格配对——和 M6 一样，pipeline 一字未改。

② group dispatch：launch_main_and_post（num_splits / memset / reduce）

去掉了那条永不可达的 throw。 M6 文档 §6 记的 O1 里，group dispatch L318-319 有一条 if constexpr(kIsDeterministic) throw "...not implemented (M6)"。M6b 真实现了 group determ，这条 throw 随之删除；kIsDeterministic 改为穿进 Problem/kernel 的真模板轴（L41 / L70 / L313+）。

3  O1 修复：group entry 一行从 BOOL_SWITCH_2 升到 3

M6 文档诚实标注过 O1：group + determ 现「静默走 atomic」，不报错也不可复现。根因是 group entry 永远以 kIsDeterministic=false 实例化 group dispatch，于是 dispatch 里 if constexpr(false) 的 determ 分支（含那条 throw）整段不编进二进制——determ 请求被静默吞掉。M6b 把这个真轴接上。

hstu_attention_group_backward_bf16.cpp（diff，O1 修复）- // softmax/deterministic compile to a runtime throw. + // M6b: kIsDeterministic is a runtime-selected template axis (causal × softmax × determ), + // so group+deterministic compiles a real determ instance instead of silently running atomic. - BOOL_SWITCH_2(param.use_causal, kUseCausal, param.use_softmax, kUseSoftmax, [&] { + BOOL_SWITCH_3(param.use_causal, kUseCausal, param.use_softmax, kUseSoftmax, + param.kIsDeterministic, kIsDeterministic, [&] { run_group_backward_dispatch<bf16_t, kUseCausal, kUseSoftmax, false, // kHasBias - false, // kIsDeterministic（硬编 → determ 不可达） + kIsDeterministic, 64>(...);
修前性质
silent-ignore，非 silent-wrong
group+determ 的梯度数值正确（atomic 路已对拍），只是不可复现且不报错——违背的是 determinism 契约，与 HANDOFF §7「silent-ignore 不可取」相悖。

group entry 直接实例化 dispatch（无 extern-template instance 文件），不像 no_group 需改 generate_instances.py。一行 BOOL_SWITCH 升级即多编出 determ 实例。
修后
group+determ 真可复现

4  ★ 高潮：抓出并修 harness group_max_seqlens_q 老洞

这是 M6b 最值得讲的一段。group determ 跑对拍时，91 个配置里恰好 1 个 dQ FAIL（max_abs_err = 0.0626 > 阈值 0.05），而且只有 softmax target 行错、dK/dV 全对。这种「极局部、单梯度」的错，往往不是机制 bug，而是某个边角输入算错了。

触发配置（lead repro）： -b=4 -nhead=4 -g=2 -seqlens=128,200,96,160 -g_local_lens=16,16 -targets=8,24,8,16 -softmax=1 -causal=1 -attn_scale=1.0 → 修前 dQ 0.0626221 FAIL。组内多 batch、异 seqlen、长 batch 带大 target、带 window —— 此前 group 测试矩阵从没同时覆盖这几条。

判别实验：把锅一步步缩到 harness

不靠猜，用三组对照实验把责任面从「determ / 库 / reference」逐一排除，最后锁死在 harness 的一个数值上：

实验观察排除了什么
同输入 group vs no_group-jagged 对照G_ref == N_ref 逐位相同（reference 对）；G_dev != N_dev，仅 batch1 target 区差（GPU 侧）排除 reference：CPU oracle 两路一致 = oracle 正确
-deterministic=0 vs =1 同配置atomic 与 determ dQ 逐位相同（都中招、错得一样）排除 determ 机制：M6b 不是元凶；错来自两路共享的上游
-g_max_seqlens override 扫描max ≥ 224 → PASS；max = 208 → FAIL；而 grid.x = ceil(·/128) = 2 两值不变排除 grid 维度：错因是 max_seqlen_q 的数值本身，不是 tile 数
三刀下去，责任面只剩一个量： max_seqlen_q 的数值。reference 对、determ 不背锅、grid 不变 ⇒ 一定是某处把 max_seqlen_q 算小了，而它被 atomic 与 determ 共享的 PRE 阶段用作 grid 上界。坏 token 恰落在 [208, 224) = [低估的 max_seqlen_q, batch1 真实 seqlen)。

数据流：低估的 max_seqlen_q 如何一路烂到 dQ

图2：harness 低估 max_seqlen_q 的数据流。PRE hstu_bwd_dot_do_o_kernel 的 grid 按 max_seqlen_q 开，落在 [max_seqlen_q, 真实 seqlen) 的尾 token 从不被计算 D（且 d_dev 未 memset）→ 垃圾 D → dS=P·(dP−D) 错 → dQ 错。只 softmax（SiLU 无 PRE-D）、只 dQ、只 target 行。

根因到行：组下标索引逐 batch 数组

example_hstu_attention_bwd.cpp · run_group_hstu_bwd（diff）// 旧式：单组 uih-max + 末尾加 num_targets[i_grp]（组下标 → 逐 batch 数组，取错 target） - group_max_seqlens_q[i_grp] = group_max_uih_seqlens_q[i_grp] - + group_contextual_seqlens[i_grp] - + (num_targets.empty() ? 0 : num_targets[i_grp]); // ✗ 组内最长 packed batch≠batch[i_grp] 时低估 // 新式：组内逐 batch 真最大，与 cu_seqlens offset 公式一致（构造上恒不低估） + for(int i = 0; i < num_batch_per_group; i++) { + const int b = i_grp * num_batch_per_group + i; + const int packed = seq_lengths_q[b] + (num_targets.empty()?0:num_targets[b]); // 逐 batch 取 + grp_max = std::max(grp_max, packed); + } + group_max_seqlens_q[i_grp] = grp_max + group_contextual_seqlens[i_grp];
一个下标错。 num_targets 是逐 batch 数组，旧式却用组下标 i_grp 去索引它，又把它加到「单组 uih-max」上。当组内最长 packed 的 batch ≠ batch[i_grp] 时，这个 max 就低估。新式改成对组内每个 batch 取 seq_lengths_q[b] + num_targets[b] 的真最大再加 ctx——与 packed offset 环里真实 batch_seqlen = seq_lengths_q[b]+num_targets[b]+ctx_grp 同源，构造上恒 ≥ 任一 batch。

防御：守卫 + 注释，但不 memset 兜底

example_hstu_attention_bwd.cpp · 加守卫（offset 环内，host 有逐 batch seqlen，便宜） // Precondition (M6b): max_seqlen_q 必须覆盖每个 batch 的 packed seqlen，否则 PRE D kernel // 和 fwd grid 会漏算该 batch 尾 token → 垃圾 D / 缺 O,LSE → dQ 错。响亮失败，别 silent-wrong。 HSTU_CHECK(max_max_seqlen_q >= batch_seqlen, "group max_seqlen_q under-covers a batch's packed seqlen ...");

HSTU_CHECK 守卫
把「喂错 max_seqlen_q」从 silent-wrong 变响亮 abort。host 本就有逐 batch seqlen，零成本。reviewer 实测：改回旧公式 → 触发配置直接 loud abort。
防御 2
PRE 前置条件注释
PRE kernel / dispatch 文档化「max_seqlen_q 必须 ≥ 所有 batch packed seqlen」。设备端 offset 的 host 校验成本高，lead 同意不做。
明确不做
不 memset d_dev 兜底
memset 后真 token 的 D=0 仍是错值（只是从垃圾变成确定性错），那是掩盖不是修复。lead 批复明令禁止。
顺带受益的两处。 同一修正后的 max_max_seqlen_q 也喂给 harness 内调 group fwd 产 LSE 那处（否则 fwd grid/LSE 同样 under-cover）和 SiLU group 在 attn_scale==0 的 scale_p fallback（1/group_max_seqlen_q）——一处修复三处一致。

5  辨析：上游 fwd 同形，但不是 bug

必须把两件事分清楚，否则容易误传：M6b 修的是我们自己的 bwd 测试 harness；上游 example_hstu_attention_fwd.cpp 里有形式相同的 group_max_seqlens_q 写法，但经与 fwd 代码作者核实，那不是 bug，是 example 的用法约定。

记录一次差点误报（诚实 + 教训）。 M6b 当时（done.md §6 / reviewer B6）曾建议「向上游报同款低估」。后续回到代码 + 找 fwd 作者核实用法约定，撤回该建议——以 HANDOFF.md §6 的最终定性为准（早期把上游过度定性为 bug 的草稿 / HTML 已作废）。教训：对他人代码下 bug 定性前，先回到代码 + 找 owner 核实用法约定，别凭对拍 FAIL 就判 bug。而我们自己的 bwd harness 不同——它默认推导就错、无人负责 override，是确凿要修的 setup bug。

6  过程纪律：四方闭合，独立复核拦下夸大

这个里程碑的价值一半在代码，一半在过程——它两次被「独立复核」文化拦下不实声称。如实呈现。

纪律点 1：带 FAIL 不 promote

coder 首轮把 candidates 标 promoted、reason 写「hetero ... PASS」,但 run-M6b-correctness.log 实为 9 PASS / 1 FAIL——过度声称，违反「日志与结论必须一致」铁则。lead 打回，candidates 改回 in-progress，修复后才转 promoted、reason 如实。

纪律点 2：reviewer 对抗实验，证回归案真能锁洞（还揪出一个空挡）

新增 3 个精确触发锁定案。reviewer 不信自述，亲手把 harness 公式改回旧式实测每个回归案是否真触发原 bug：

为何 SiLU 案锁不住（结构上不可能）： reviewer 逐一证伪三条路——① SiLU 路无 dot_do_o PRE-D kernel，under-cover 无 D 可坏（bug 唯一发源）；② grid 按 kM0=128 瓦化，208 vs 224 都 ceil(/128)=2 同 tile 数，长 batch 尾行仍被 MAIN 覆盖；③ scale_p fallback 向量 GPU 与 reference 同吃一份，错的 scale 两侧抵消（实测 dQ err=0 仍 PASS）。结论:本 bug 本质 softmax-PRE-D 专属,已被 sm-atomic+sm-determ 有效锁定;silu-atomic 是冗余覆盖而非 lock,其 note「locks ... grid/scale_p」夸大,reviewer 建议改措辞(非阻塞,洞已堵)。
守卫触发路与派单设想不同（reviewer B3，诚实记录）： 派单原设想「喂小 -g_max_seqlens → 应 abort」,实测不 abort——因 override 现为 max(...) 只增不减,小值被真实 per-batch max 压住,根本构造不出低估(比靠 assert 兜更强的安全姿态)。HSTU_CHECK 退化为防「未来有人改坏公式」的护栏,reviewer Exp1(改回旧公式)证其可达。
