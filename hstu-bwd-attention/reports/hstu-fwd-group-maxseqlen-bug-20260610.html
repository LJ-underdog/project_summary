一个组下标错位如何让整个 forward 算出 NaN：HSTU group fwd 的 max_seqlen_q 低估 bug

这份文档把一个单字符级别的索引错误（num_targets[i_grp] 本该是 [i_batch]）讲透：它怎么让 group forward 的 max_seqlen_q 被低估，怎么经由 GridSize / m-tile / split-kv 把整个 launch 带偏，从而让 O 与 LSE 全局算错（含 NaN）——而不是只错尾部 token。并演示如何严谨地证明它是真 bug（绕开「双错相等」陷阱的三路硬证据）。已实测确认，default 用法即触发。

读者：要判断「要不要报上游 / 怎么修」的工程师，以及想学「怎样确认一个 silent-wrong bug」的人
代码：example/ck_tile/18_hstu_attention/example_hstu_attention_fwd.cpp  ·  分支 hstu_attention_fwd（tip cde6f606） ·  环境 gfx950 / MI350X  ·  2026-06-10  ·  关联 M6 文档
TL;DR — 一句话看懂这个 bug

group forward 的 host 端在算 group_max_seqlens_q 时，用组下标 i_grp 去索引一个逐 batch 的 num_targets[] 数组（example_hstu_attention_fwd.cpp:851）。当一个组里「最长的那个 packed batch」不是第 i_grp 个 batch 时，max_seqlen_q 被低估。而 max_seqlen_q 驱动 GridSize / m-tile / split-kv 的选择——低估一传十，整个 launch 配置偏掉，GPU forward 的 O 与 LSE 因此全局算错。

实测（seqlens=100, targets=0,0,0,200, g=2）：该组应取 300，却取了 0 → max_seqlen_q 算成 100（漏 200）。结果 O 87.5% 元素错（含 NaN/inf）、LSE 84.6% 错。这是 default 参数派生路径（不传 -g_max_seqlens）就会中的——即上游正常用法。

O 87.5% wrong（含 NaN） LSE 84.6% wrong default 用法即触发 三路硬证据确认真 bug host 端逻辑、架构无关

1  背景：group / packed 布局长什么样

HSTU group 模式把多个 batch 的 token 沿一维紧密拼接成 packed 张量（dim0=1），用 cu_seqlens（前缀和 offsets）定位每个 batch。每个 batch 的「packed seqlen」= uih + target (+ contextual)。group 则是把相邻 num_batch_per_group 个 batch 归为一组、共享一套超参。

图1：g=2、4 batch 的 packed 布局。group1 = {batch2, batch3}，其中 batch3 带 target=200，真实 packed seqlen = 300，是组内最长。cu_seqlens 的 offset 公式（:869）用 per-batch 下标 num_targets[i] —— 这是 token 布局的「真相」。

2  max_seqlen_q 是什么、喂给谁

max_seqlen_q = 所有 batch packed seqlen 的上界，kernel 用它来决定启动配置。它必须 ≥ 每个 batch 的真实 packed seqlen，否则「覆盖不全」。它不是一个无关紧要的标量——它进了三个决定 launch 形状的函数。

图2：max_seqlen_q（:1000 进 params）驱动 GridSize(:166) / get_hstu_attention_fwd_mtile(:186) / shall_use_splitkv(:205) 三处启动配置。它一旦低估，整个 launch 形状就偏——不是只丢尾巴。

关键直觉： max_seqlen_q 不是「输出张量的某个边界」，而是「怎么把工作切成 block」的依据。切错了，受影响的不只是没被覆盖的那段 token，而是整个网格的 tile→token 映射与跨 split 归约。这就是为什么后面会看到 b0/b1/b2 即便完全落在网格内也算错。

3  bug 本身：组下标索引了 per-batch 数组

同一个 harness 里有两套量：group_max_uih_seqlens_q[] 是 per-group（长度 num_group，:809-822 用内层 batch 循环正确求 max），而 num_targets[] 是 per-batch（长度 num_batch，:776 supplement）。出错的一行把它们的下标混用了。

正确公式 vs 错误公式（并排）

example_hstu_attention_fwd.cpp:850-851（实际代码，bug 所在）// ✗ 错误:num_targets 用 GROUP 下标 i_grp 索引 PER-BATCH 数组 group_max_seqlens_q[i_grp] = group_max_uih_seqlens_q[i_grp] + group_contextual_seqlens[i_grp] + num_targets[i_grp]; // ✓ 正确:应在组内 per-batch 取 max(uih + target),与 offset 公式 :869 一致 int gmax_q = 0; for(b in group i_grp) gmax_q = max(gmax_q, seq_lengths_q[b] + num_targets[b]); // per-batch 下标 b group_max_seqlens_q[i_grp] = gmax_q + group_contextual_seqlens[i_grp];
两个错叠加： ① 下标错——num_targets[i_grp] 取的是「第 i_grp 个 batch」的 target，而不是「组内最长 packed batch」的 target；② 运算错——它把 target + 到「组内 uih 的 max」上，但 uih 的 max 和这个 target 可能来自不同 batch。正确做法是先在 batch 内把 uih+target 加好、再跨 batch 取 max（「只增不减」），而不是「max 完再加一个错位的 target」。

具体例子：取错了哪个元素（核心图）

图3（核心）：group1 = {batch2, batch3}。代码用 num_targets[i_grp=1] 取到 batch1 的 target=0（与 group1 毫无关系）；正确应取组内最长 packed batch（batch3）的 target=200。结果 max_seqlen_q 被算成 100 而非 300，低估 200。

为什么 group_max_uih 是对的、就这一项错？ group_max_uih_seqlens_q[i_grp] 在 :809-822 是用内层 batch 循环正确地对组内 uih 求 max 的。bug 只在 :851 这一项——它没有对组内的 target 也做同样的「循环取 max」，而是图省事直接 + num_targets[i_grp]，既错了下标、又错了「先加后 max」的顺序。

4  为什么是「全局错」而不是「只错尾巴」

直觉上，低估 max_seqlen_q 似乎只该影响「没被覆盖的那段 token」（batch3 的 [100,300)）。但实测显示 b0/b1/b2 也错、还有 NaN。原因在第 2 节：max_seqlen_q 决定的是整个 launch 的切块方式。

两类损坏叠加： ① under-cover：batch3 的 [100,300) 根本没有 block 去算（grid 按低估的 100 开）；② 全局错切：m-tile / split-kv 选了错误的档，使每个 batch 的 tile→token 映射和跨 split 归约都偏，于是连完全落在网格内的 b0/b1/b2 也产出错值。再叠加未初始化 / 越界读 → NaN/inf。实验 3（mild trigger，seqlens=256 短 batch 满 tile 覆盖）仍全错，进一步坐实「不是局部尾巴问题」。

另一个独立佐证：mild trigger（-seqlens=256 -targets=0,0,0,200，让短 batch 本可被满 tile 覆盖）下 O 仍 64.2% 错、LSE 58.1% 错——b0/b1/b2 在网格内却错，说明低估腐蚀的是全局输出。

5  怎么证明这是真 bug（方法论亮点）

「GPU 与 reference 对不上」不足以断定 GPU 错——也可能是 reference 也用了同一个错值（双错相等反而会「假 PASS」；这里是反过来：要排除「两边都被 max_seqlen_q 影响导致对比无意义」）。严谨确认需要先证明 reference 不依赖被怀疑的量，再用多路独立实验。

第一步：证明 reference 对 max_seqlen_q 独立（绕开双错陷阱）

reference_hstu_attention_fwd.hpp（group, softmax 路）L433: int seqlen_q = seq_q_offsets[i_batch+1] - seq_q_offsets[i_batch]; // 真实 per-batch offset 长度 L436: int num_target = num_targets.empty() ? 0 : num_targets[i_batch]; // per-batch,正确 L438: int max_seqlen_q = group_max_seqlens_q[i_group]; // 仅用于 scale_p / mask 维度
关键事实： reference 算每个 batch 的 O/LSE 用的是真实 offset 长度（:433）和 per-batch 的 num_targets[i_batch]（:436，正确下标）。max_seqlen_q（:438）只用于 ① SiLU 的 scale_p=1/max_seqlen_q（softmax 路不用）和 ② mask 张量维度。所以在 softmax 路下，reference 的 O/LSE 与 max_seqlen_q 无关——它不会跟着 GPU 一起错。这使得「GPU vs reference 不一致」能真正反映 GPU 的错，而非双错相等的假象。

实测坐实独立性：trigger 与 control 两次跑出的 reference output_host.dat / lse_host.dat BYTE-IDENTICAL（cmp 通过）——证明 reference 确实与 max_seqlen_q 无关。

第二步：三路独立硬证据（互证）

6  修法

核心思想：把「max 完再加一个错位 target」（可能低估）改成「组内 per-batch 先算 uih+target、再跨 batch 取 max」（只增不减），与 cu_seqlens 的 offset 公式（:869）严格一致。

建议 patch（与 bwd M6b 同源；example_hstu_attention_fwd.cpp:850-854）int gmax_q = 0, gmax_kv = 0; for(int b : batches_of_group(i_grp)) { int tgt = num_targets.empty() ? 0 : num_targets[b]; // per-batch 下标 b gmax_q = std::max(gmax_q, seq_lengths_q[b] + tgt); gmax_kv = std::max(gmax_kv, seq_lengths_kv[b] + tgt); } group_max_seqlens_q[i_grp] = gmax_q + group_contextual_seqlens[i_grp]; group_max_seqlens_kv[i_grp] = gmax_kv + group_contextual_seqlens[i_grp]; // 若支持 -g_max_seqlens override:用 max() 并入,而非 replace(避免再次低估) // 另:加 assert(max_seqlen_q >= 每 batch packed seqlen) → silent-wrong 变响亮失败
对比 1
replace vs max
错误式是「= 某个可能偏小的值」（replace，可低估）；正确式是「= max(…)」（只增不减），结构上杜绝低估。
对比 2
先加后 max
必须在 batch 内先把 uih+target 加好再跨 batch max，不能 max 完 uih 再加一个别处的 target。
防御
assert 兜底
加 assert(max_seqlen_q ≥ 每 batch packed seqlen)，把未来的 mis-setup 从 silent-wrong 变成响亮失败。

结论与建议： 这是 host 端逻辑 bug、架构无关，在 default 参数路径（不传 -g_max_seqlens）即触发，且直接腐蚀 forward 主输出 O+LSE（含 NaN）。bwd 同款已在我方修复；fwd 出现在上游维护的 example_hstu_attention_fwd.cpp，建议向上游报告（issue 草稿已备）。修法是 6 节的 per-group 取 max + assert，与 bwd M6b 同源。
诚实边界（不夸大）： ① 这是 example/harness 的 host 端计算 bug，不是库 kernel 本身的 bug——库 kernel 依赖调用方传入正确的 max_seqlen_q（contract）。② 触发需要组内异构 + 最长 batch 非组首；同构或单 batch/组不触发。③ 数字（87.5%/84.6%/NaN）来自一个具体 repro（seqlens=100,targets=0,0,0,200），不同配置比例不同——但「全局错 + 可复现 + 三路证据」的定性结论稳健。
