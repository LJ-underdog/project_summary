TL;DR — 一句话看懂 M2

M2 没有重新实现 mask。HSTU 的 5 因子掩码语义（causal / window / contextual / min_full / num_target）早在 fwd 的 IsTokenPairInsideMask 里就写好了 —— M2 做的是补上 bwd 方向缺的两个 helper（GetTileRangeAlongY / IsEdgeTile）、在反向 pipeline 的 STAGE2 上逐像素清零 masked-out 位置、再把 dispatch / kernel 接线到这套现成 mask 上。

1  总览：M2 到底改了什么

M2 = 在 M1（no-mask SiLU bwd）已通过的基础上，把 HSTU 的 5 因子掩码接进反向。核心理念一句话：复用 fwd 的 mask 语义，只补 bwd 方向缺的部分，再接线。

白话：M2 的四件事

  • ① 补 helper（hstu_block_masking.hpp）：给 4 个 HSTU mask struct 各加 GetTileRangeAlongY（KV-block → 该读哪些 Q 行）和 IsEdgeTile（这块 tile 是否需要逐像素检查）。纯加，不动 fwd 任何成员。
  • ② 逐像素置零（...no_softmax_bwd_pipeline.hpp STAGE2）：算完 p、g 后，对「边缘 tile」上 IsTokenPairInsideMask 为假的位置，把 p、g 显式写 0。
  • ③ kernel 构造 mask（...bwd_kernel.hpp）：kargs 加 4 个 HSTU mask 标量，按 kUseLocal 调 make_hstu_self_attention_block_mask_*，复刻 reference 的 min_full 钳制。
  • ④ dispatch 接线（...batched_backward_dispatch.hpp）：去掉 causal 的 throw，用 BOOL_SWITCH(window>0) 在运行时选 local / non-local 的 HSTU mask 类型。
为什么「复用而非重写」是对的？ HSTU 的 5 因子掩码逻辑在 fwd 已经过完整验证。反向的掩码语义与正向完全一致（同一对 (q,k) 在前向被遮蔽，反向的 dS 就该是 0）。重写一份等于凭空多一份要维护、要对拍的代码 —— M2 选择把同一份 IsTokenPairInsideMask 直接拿来用，差异只在「方向相关」的少量 helper。
一个关键诚实声明（先打预防针）： git status 会显示 ~202 个改动文件，但其中 198 个是 fwd instance 文件，它们只因为重跑了 generate_instances.py 而被改写，每个文件只动了 1 行注释路径（composable_kernel/… → ck_hstu/…），与 M2 逻辑无关。真正含 M2 mask 逻辑的已跟踪文件只有 1 个（hstu_block_masking.hpp），其余 M2 改动都在新增（未跟踪）的 bwd 文件里。详见 §2。

4  mask 成员新增（以 git diff 呈现）

这是 M2 唯一一处「已跟踪文件」的 mask 逻辑改动，git diff hstu_block_masking.hpp 在 4 个 struct 各加同形的两个成员。下面贴 Self-No-Local 的真实片段（其余 3 个 struct 仅 seqlen vs seqlen_q 命名差异）。

设计要点 1
Y-range 首版 = 保守全扫
返回 (0, seqlen) 而非真实紧致区间。这是 DESIGN §8.2-R3 的 fallback B：宁可多扫、不可漏算。漏掉一行 Q 会让该行梯度错；多扫只是慢。收紧到真实 Y-range = perf 项（M8）。
设计要点 2
IsEdgeTile 复用 + 参数序
IsEdgeTile := !IsFullTileInsideMask。注意调用时把 (TileWidth, TileHeight) 按 IsFullTileInsideMask 的 (W, H) 形参顺序传 —— 反向 tile 的高宽（M0 行 × N0 列）与该函数签名需对齐，写反会误判。
为什么 HOST_DEVICE
让离线校验能在 CPU 调
GetTileRangeAlongY 标 CK_TILE_HOST_DEVICE，这样 §7 的离线校验器能在 host 端直接调它、对每个 tile 断言超集成立 —— 这是「信任 GPU mask」的前置。

5  【图2】masked-out 置零数据流 + STAGE2 代码

M2 的正确性核心：在边缘 tile 上，把被遮蔽位置的 p（→dV）和 g（→dS）显式写 0，让 masked 对在后续所有梯度里都不留痕迹。

图2：edge tile 上逐像素把 p、g 清零 → g=0 使 STAGE5 的 ds 自动为 0 → 三个梯度都不受 masked 对污染，等价于 reference 的 dS=0。

STAGE2 真实代码片段

6  dispatch / kernel 接线（怎么连起来）

M2 把「选哪种 mask 类型」放在 dispatch（编译期 + 运行时 BOOL_SWITCH），把「用什么参数构造 mask 对象」放在 kernel。两段拼起来，STAGE2 才拿得到正确的 mask。

图3：dispatch 选类型（causal 编译期、local 运行时 BOOL_SWITCH）→ MakeKargs 带 mask 标量 → kernel 用 per-batch 参数构造 mask 对象，喂给 pipeline。

7  离线校验器：为什么先写它

GetTileRangeAlongY 现取保守超集 —— 但「保守」必须被证明：返回的区间真的包含所有该 attend 的 Q 行吗？漏一行就是错梯度。M2 把这件事做成一个 host 端离线程序，在上 GPU 前断言到底。

断言（对每个 KV tile）： [y_start, y_end) ⊇ { sq : ∃ sk ∈ tile, IsTokenPairInsideMask(sq, sk) }

8  抓修的 bug：harness 漏了 num_targets 补齐

这是 M2 过程里一个真实发现，值得单独讲：num_target 档一开始 FAIL，根因不在 kernel mask，而在对拍 harness 少上传了几个 int。

症状
num_target 档 FAIL
-targets=16 在 b=2 下误差直接到 ref 量级（不是舍入级）。其它档全 PASS，唯独带 num_target 的炸。
根因
只上传 1 个 int
-targets=16 解析成长度 1 的数组，但 kernel 与 reference 都按 num_targets_ptr[i_batch] 取。i_batch=1 时读 ptr[1] —— 越界，batch1 的 mask 全错。
修法
补齐到 num_batch
harness 加 supplement_array_by_last_element(num_targets, num_batch)，用末元素补满。补后立即 PASS。
example_hstu_attention_bwd.cpp（修复，~L72–82 + L157–162）template <typename T> static void supplement_array_by_last_element(std::vector<T>& arr, int target_num_elements) { if(static_cast<int>(arr.size()) < target_num_elements) { T last_val = arr.back(); for(int i = arr.size(); i < target_num_elements; i++) arr.push_back(last_val); } } ... if(!num_targets.empty()) // supplement to num_batch (kernel + reference index num_targets[i_batch]) supplement_array_by_last_element(num_targets, num_batch);
同源问题也存在于 reference。 CPU oracle 同样按 num_targets[1] 取值（同样 UB）。补齐 harness 后，GPU 与 reference 喂的是同一份补满的数组，两边一致 → 对拍 PASS。这说明 bug 在「喂数据」层而非「算梯度」层 —— 一个容易被误判成 kernel 错的陷阱。

10  遗留与边界（诚实标注）

  • perf：Y-range 现为全 Q 扫描。GetTileRangeAlongY 返回保守超集，正确但每个 edge tile 都逐像素跑 IsTokenPairInsideMask，偏慢。收紧为真实 Y-range + 启用 tile 级 is_tile_in_first_split 跳过 = M8。
  • cross-attention mask 成员已加但 bwd 暂只构造 self。4 个 struct（含 Cross）都补了 GetTileRangeAlongY/IsEdgeTile，但 bwd_kernel.hpp 目前只调 make_hstu_self_attention_block_mask_*；cross 路径待对应里程碑接。
  • 覆盖面边界（沿用 M1）：仍限 batched / SiLU / bf16 / hdim64 / atomic。jagged(M3) / group(M4) / softmax(M5) / deterministic(M6) / fp16+hdim128(M7) 仍按设计 throw 或 skip。
  • 无未解决阻塞点。
给 reviewer 的一句话总结： M2 是一次「克制的接线」—— 掩码语义零重写，新增面只有两个 helper + 一段 STAGE2 置零 + dispatch/kernel 接线 + 一个 harness bugfix。git status 的 202 文件里，198 个是 fwd 再生成噪音，真正要 review 的 mask 逻辑集中在 hstu_block_masking.hpp 的 diff 和那段 STAGE2。
