HSTU Attention Backward — M7b：把 hdim 从「写死 64」改成「随 MaxK 选 tile」，且一行 kernel 不碰

这份文档讲清 M7b 如何把 bwd 从 仅 hd64 扩到 symmetric hdim ∈ {64,96,128,256}（hdim_qk==hdim_v）。核心是一处差点静默出错的设计缺陷：pre-M7b 的 dispatch 把 hd64 的 tile shape 写死，MaxK 只流进 instance 符号、没用来选 shape——若直接加 headdim 轴，四个 hdim 会静默共用同一份 hd64 tile（silent-wrong）。M7b 用一个 HstuBwdShape<MaxK> selector 把 tile 变成 MaxK 的编译期函数，并用 二进制符号反证证明 tile 真的随 hdim 分化了。范围诚实标注：仅 symmetric，hdim_qk≠hdim_v 与非典范 hdim 是 M7c（guard 显式 throw 挡住）。所有片段引磁盘真实行号（commit 1ae97750，基线 bf82a1d2）。

代码目录：ck_hstu/example/ck_tile/18_hstu_attention/  ·  主目标 gfx950 (MI350X/CDNA4)  ·  落点 2026-06-11  ·  接续 M7a fp16 文档
TL;DR — 一句话看懂 M7b

bwd 的 dispatch/kernel/pipeline 全都按 Problem（内含 FmhaBwdShape）模板化——shape 是注入的。M7b 只做一件事：把两个 dispatch 里写死的 hd64 tile 换成 using FmhaBwdShape = HstuBwdShape<MaxK>::Type;，让 tile 随编译期 MaxK 选。新增 selector 头文件（四特化 64/96/128/256，蓝本 = 上游 FMHA bwd codegen gfx9 非 trload preset），entry 把硬编码的 64 换成 HDIM_SWITCH，generate_instances 加 headdim 轴。promoted 的 pipeline / kernel / reference 一行未改（git diff 为空）。

最关键的设计点：HstuBwdShape<64>::Type 与原硬编码逐字等价 ⇒ hd64 路实例化出 byte-identical 的 kernel = 零回归基石；非典范 / 非对称 hdim 经入口 guard 显式 throw（不静默 pad）。tile「真随 hdim 分化」用 rocprofv3 抽二进制符号反证：kernel 的 LDS 出现 32 / 48 / 64 KB 多档——若静默复用 hd64，应恒 32 KB。

1  M7b 是什么：解禁 symmetric hdim {64,96,128,256}

M7b 把反向支持的 head-dim 从 {64} 扩成 {64, 96, 128, 256}，约束是 hdim_qk == hdim_v（symmetric）。不动 dtype（bf16+fp16 已由 M7a 通）、不动任何 kernel 算法、不引入 head-dim padding——目标只取四个能被 tile 整除的典范值，故每个 hdim 都 hdim==bhdq==bhdv==MaxK，padding 恒为 0。

In scope
symmetric 典范 hdim
hdim_qk == hdim_v ∈ {64, 96, 128, 256}。每个映射到精确同值的 MaxK tile，无 pad。
Out of scope → M7c
非对称 hdim
hdim_qk ≠ hdim_v（如 64/128）需独立 q/v tile + pad 路。入口 guard 显式 throw。
Out of scope → M7c
非典范 hdim
如 80 / 100：HDIM_SWITCH 会向上圆到大 tile，需 head-dim padding。guard throw,不静默算错。
白话： M7b 是「让现成的 5-GEMM bwd kernel 换更大的 tile 跑起来」，不是「写新算法」。难点不在算法，在怎么保证换 tile 时既没把 hd64 弄回归、又没让新 hdim 静默用错 tile——这正是下面几节的主线。

2  核心洞察：MaxK 穿透了，却没用来选 shape

这是整单的「地雷」。pre-M7b 的两个 dispatch 模板签名上已经有 MaxK，instance 文件名也带 maxk_64——看上去「hdim 是个轴」。但 tile shape 是硬编码的 hd64 常量，MaxK 只活在符号名里、从不参与 shape 构造。

陷阱推演（若不修就加 headdim 轴）： generate_instances 把 BWD_HEADDIMS 改成 [64,96,128,256] ⇒ 生成 4 份 kernel,MaxK = 64/96/128/256 各异（符号名不同） 但 FmhaBwdShape 仍 = 写死的 hd64 tile（bm0=32,bn0=128,bhd=64,…） ⇒ 四个「不同 hdim」的 kernel 跑的是同一份 hd64 tile = silent-wrong （能编译、可能还「PASS」,但 head-dim 维度算错——最危险的那种 bug）

【图1】修复前后：shape 从哪来

图1：左 = pre-M7b，MaxK 仅进符号名、tile 写死 hd64，加 headdim 轴会四 hdim 共用 hd64 tile（silent-wrong）。右 = M7b，HstuBwdShape<MaxK> 让 tile 成为 MaxK 的编译期函数,四特化各异。

为什么这是「最值得讲」的点： 它是能编译、能跑、甚至能 PASS 的错——最难发现的 bug 类。draft 阶段把它揪出来,定了铁律：「shape 必须随 MaxK 选；headdim 轴必须在 shape 选择就位之后才加。」整单顺序由此而定（§6）。

3  shape selector：HstuBwdShape<MaxK> 四特化

新增 hstu_attention_bwd_shape.hpp：一个 template<index_t MaxK> struct HstuBwdShape;，对 64/96/128/256 各一特化，导出 using Type = TileFmhaBwdShape<…>。primary 模板故意不定义——只有四个典范 hdim 合法,别的值编译期就报错。tile 数值蓝本 = 上游 FMHA bwd codegen 01_fmha/codegen/ops/fmha_bwd.py 的 gfx9 fp16/bf16 非 trload preset（gfx950 非 trload 继承之）。

四个 hdim 的 tile 参数（FmhaBlockTile = sequence<bm0,bn0,bk0,bk1,bk2,bk3,bk4,bhdq,bhdv>）

读表： tile 不是「同一份放大」——96 的 Gemm4 warp 布局变 2,2,1，128/256 的 q-block 减到 16,256 的 k-block 又减到 64。每个值都对得上 codegen 蓝本（reviewer 逐字符核对）。第 10 个模板槽（Gemm4 warp tile）复用 WarpTile0 而非蓝本的 min(wk0,bk4)——因为四个 hdim 都 wk0=32 且 bk4=32 ⇒ min=32=wk0,故复用恒等价。

零回归基石：<64> 特化与原硬编码逐字等价

两个 dispatch — 唯一改动：取 selector 而非写死// pre-M7b: 30+ 行硬编码 FmhaBlockTile/BlockWarps/WarpTile/TileFmhaBwdShape …（删除） using FmhaBwdShape = typename HstuBwdShape<MaxK>::Type; // ← 全部替换成这一行
白话： <64> 的 sequence 值、TileFmhaBwdShape 的 11 个类型实参顺序、末尾 0（kMaxSeqLenQ）都和原硬编码逐字相同 ⇒ MaxK=64 路实例化出同一个类型 ⇒ byte-identical kernel。「selector 同型即同码」,不需要 if constexpr(MaxK==64) 走旧路那种 hack。证据见 §9。

4  guard：把 silent-wrong 变成响亮的 throw

entry 用 HDIM_SWITCH(hdim_qk, hdim_v, MaxK, …) 把运行时 hdim 映射到编译期 MaxK,规则是 ≤64→64, ≤96→96, ≤128→128, ≤256→256, else throw。问题：非典范值会被向上圆——hdim=100 会选 MaxK=128 的 tile,但实际只有 100 维数据,而 M7b 不做 pad ⇒ 读 100..127 维是越界垃圾 = silent-wrong。

两 dispatch 的 Run() 入口 — 替换原 3 处 hd64-only throw// M7b: symmetric hdim ∈ {64,96,128,256}; 要求 hdim_qk==hdim_v==MaxK, // 使 head-dim 精确贴合 tile（无 pad）。挡住 HDIM_SWITCH 会向上圆的非典范 hdim。 if(param.hdim_qk != param.hdim_v || param.hdim_qk != MaxK) throw std::runtime_error( "HSTU bwd ... supports symmetric hdim_qk==hdim_v in {64,96,128,256} only");

图2：guard 把「非典范 / 非对称 hdim」从可能的 silent-wrong 转成显式 throw。两个 reject 测试案（hdim=100、hdim_qk=64≠hdim_v=128）实测均 throw + exit -6 + 正确 what()。

反证机理（为何 guard 必需）： 若去掉 guard,hdim=100 会走 hd128 tile（bhdq=128）而实际 hdim=100,kernel 的 buffer_load 越界补 0 ⇒ 产出非 throw 的错值。guard 在场时实测 throw,证明这条防线真在挡洞。

5  harness kN0 修复：hd256 的 bn0=64 牵出的越界

deterministic dQ 把 dq_acc 拆成 num_splits 个 slot（每个 KV-block 一个,POST 阶段归约）。num_splits = ceil(grid_seqlen_kv / kN0),而 kN0 = Pipeline::kN0 = BlockTile::at(1) = bn0(k-seqlen block)。pre-M7b 所有 hdim 的 bn0 都是 128,harness 就写死 kN0_bwd=128 来算 workspace 大小。

hd256 的 tile：bn0 = 64（不是 128!） 若 harness 仍用 kN0=128 估 num_splits ⇒ 估值 = 实际的一半 但 dispatch 用 Pipeline::kN0=64 实际拆 2× 份 ⇒ determ workspace 写越界 / reduce 读错 → 静默错 dQ
example_hstu_attention_bwd.cpp — 两处（no_group + group）随 hdim 取 kN0// hd256 的 preset 用 bn0=64（其余 hdim 用 128）— 必须匹配 dispatch 的 Pipeline::kN0 - constexpr int kN0_bwd = 128; + const int kN0_bwd = (hdim_qk == 256) ? 64 : 128;
这是 M7b 唯一有「真 bug 风险」的改动（其余是结构性重构）。验证：hd256 deterministic 对拍 PASS（dQ err 0.0156 vs |ref|≈10.7）且 同输入两次跑 byte-identical（no_group + group 各一案）。反推：若 hd256 误用了 hd64 tile（bn0=128），harness kN0=64 与 dispatch 失配 → determ 对 oracle 应 FAIL。实测 PASS ⇒ 反证 bn0=64 的 hd256 tile 真在用。

6  分阶段落地：先证「重构零回归」,再加 hdim

由 §2 的铁律（shape 选择必须先就位）推出实现顺序：把单子切成两 stage,中间立一个 lead 亲验的硬检查点——先只做重构（不加新 hdim）、证明它零回归,再开闸加 96/128/256。

图3：两阶段 + 硬检查点。stage1 只重构、不加 hdim,先把「换 selector 没动行为」证死;通过后才在 stage2 加 hdim,从最常用的 hd128（2 幂）起增量推进。

为什么值得分两段： 如果把「重构」和「加 hdim」混在一起,一旦对拍出错,无法判断是重构碰坏了 hd64 还是新 hdim 的 tile 错。分段 + 检查点把这两类风险解耦——stage1 绿了,后续任何问题都只可能在新 hdim。

7  二进制符号反证：tile 真随 hdim 分化了吗？

§2 的地雷最阴险之处：就算 tile 静默复用 hd64,代码也能编译、可能还 PASS。光看「对拍绿了」不足以证明 tile 真的分化。M7b 用一个不依赖对拍结果的独立物证把这点钉死——直接看编译出的二进制里,各 kernel 的资源占用。

反证逻辑：LDS 占用是 tile 的「指纹」 LDS（共享内存）大小由 tile 形状决定 → tile 不同 ⇒ LDS 不同 若四 hdim 静默共用 hd64 tile ⇒ 所有 bwd kernel 的 LDS 应恒 = 32 KB rocprofv3 实测：kernel 符号的 LDS 出现 32 KB / 48 KB / 64 KB 多档并存 ⇒ tile 确实随 hdim 分化,非静默复用 hd64

【图4】rocprofv3 抽二进制 kernel 符号的 LDS 分布

图4：二进制里 bwd DQDKDV kernel 的 LDS 占用呈 32 / 48 / 64 KB 多档。若 tile 静默复用 hd64,应恒 32 KB。多档存在 = tile 确实随 hdim 分化（独立于对拍的物证）。

这条为什么单列： 它把「复用模板加 hdim」最容易漏的失败模式（tile 没真分化、对拍假绿）变成可证伪的——不看代码、不信对拍,直接量二进制。多档 LDS 对得上四 tile 的理论值 ⇒ 放心。配合 §5 的「hd256 determ 用 kN0=64 才 PASS」,双重锁死。

8  hd256 资源：无 spill,occupancy=1 是已知 perf 特征

hd256 是四 hdim 里 tile 最大的,首要风险是寄存器溢出（spill）——一旦 Scratch>0,性能与正确性都受影响。rocprofv3 --kernel-trace 实测（gfx950/MI350X）：

能力边界（M7b 后）

SiLU + softmax 全模式（batched / jagged / group） × 全 5 因子 mask × causal{0,1} × bf16 + fp16 × symmetric hdim ∈ {64,96,128,256} × atomic + deterministic（全模式）。hd64 零回归。

范围限定（非缺口隐瞒）

M7b 仅 symmetric:hdim_qk == hdim_v ∈ {64,96,128,256}。 hdim_qk ≠ hdim_v（非对称）与非典范任意 hdim（需 head-dim padding）属 M7c,已由入口 guard 显式 throw 挡住。本文档不把范围夸大成「任意 hdim」。
  • 盲区继承 M5/M5b：LSE 数值由 GPU fwd 产、对拍两侧共用同一份,靠 fwd 里程碑兜底——hdim 未改变此结构。
  • 非阻塞观察（→ M8 perf）：hd256 occupancy=1（硬编码 launch-bounds trait,非 LDS-bound——CDNA4 每 CU LDS 160 KB,kernel 仅占 64 KB);group entry TU 单 TU 内 4 hdim × 8 combo 实例化较重（本次独立重建仍顺利,未成阻塞,过慢可拆 per-hdim instance）。
