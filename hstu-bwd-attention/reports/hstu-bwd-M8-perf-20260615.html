HSTU Attention Backward — M8 perf：先量后砍，把 MAIN 保守全扫的 q-tile 浪费收紧掉

这份文档讲清 M8 perf 里程碑如何在实测驱动下为 HSTU bwd 提速。流程是「先建测量基线（MI，behind -perf）→ rocprofv3 profile 定位真瓶颈 → 据此把 MAIN dqdkdv 的 GetTileRangeAlongY 从保守全扫 (0,seqlen) 收紧到真实 q-band」。

核心不是写新算法——profile 显示 MAIN 占 bwd 墙钟 84–90%、矩阵核闲 ~90%、且非带宽瓶颈，浪费来自 GetTileRangeAlongY 的保守全扫。两件事最值得讲：① critique 用实测证伪了 scoping 自己提的「grid starvation 根因」（数据驱动纠错）；② 离线穷举校验器在 GPU 跑之前抓到 2 个真 under-tighten bug（对拍可能漏）。scope 诚实标注：本期只做 MI + B2 + B3，占用率类（B4/B7）暂缓。所有数字引素材，commit 048f0a9a，基线 4629508f = cross-attention。

TL;DR — 一句话看懂 M8 perf

bwd 此前没有 kernel 计时设施，且 MAIN 的每个 KV-tile 都保守全扫所有 Q-tile（GetTileRangeAlongY 返回 (0,seqlen)）——causal 浪费一半、window 浪费 >90%。M8 先建 MI（-perf 计时基线，设备码 byte-identical），用 rocprofv3 定位「MAIN 主导 84–90%、矩阵核闲 90%、非带宽瓶颈」，再把 GetTileRangeAlongY 收紧到真实 q-band：B2 causal、B3 local/window。

实测 MAIN 加速 causal 1.25–1.60×、window 4.7–9.8×（诚实低于 [derived] 模型，Amdahl 归因）。安全靠离线穷举校验器（1,973,278 checks ALL GREEN）兜底——它比对拍更早更硬，抓到 2 个对拍可能漏的真 under-tighten bug。reviewer 还做 reverse-proof（破坏收紧 → 校验器 FAIL）证它非 vacuous。pipeline / kernel / reference 一行未改；scope = MI+B2+B3，占用率（B4/B7）暂缓。

1  M8 是什么 + scope：先量后砍，只做 MI + B2 + B3

M8 是 HSTU bwd 的第一个 perf 里程碑。设计经一个 scoping workflow（6 路分析，含一份 rocprofv3 实测 profile）+ critique，lead 闸门裁决本期只做 3 项 runtime 真赢，占用率类候选证据不足或被证伪，暂缓。

MI · enabler
测量基线（behind -perf）
新增 time_op 计时原语 + -perf envelope/per-kernel/5-GEMM TFLOPS。设备码 byte-identical，套件不受扰。是 B2/B3 的硬前提。
B2 · runtime
GetTileRangeAlongY 收紧 causal
NoLocal mask（self+cross）从全扫收紧到 causal 真实 q-band。MAIN 1.25–1.60×。
B3 · runtime
GetTileRangeAlongY 收紧 window
WithLocal mask（self+cross）收紧到 window 双边带 + cross/contextual/min_full 特例。MAIN 4.7–9.8×。
scope 诚实标注：本期只做 MI + B2 + B3（runtime 真赢）。 占用率类候选 B4（grid widening）依据被 critique 实测证伪、B7（hd256 occupancy / VGPR）阻塞于未解的 VGPR 矛盾，连同 B1/B5/B6/INV/B8–B10 一并暂缓（§7 逐项说明）。本文档不把 M8 说成「全面 perf 优化」。
白话： M8 不动算法、不动 tile 形状、不碰占用率，只做一件低风险高收益的事——别再扫那些对当前 KV-block 零贡献的 Q-tile。难点不在「砍」，而在怎么证明砍得不多不少（不漏梯度），以及先靠数据确认这真是瓶颈——这正是 §2 与 §5 的主线。

2  实测驱动（亮点）：profile 定瓶颈 + critique 证伪自己的根因

M8 不是「猜哪里慢就改哪里」。一份 rocprofv3 profile（canonical bf16 b2 nhead8 seqlen2048 causal softmax hd64）把瓶颈钉死，又在 scoping 阶段用实测推翻了自己最初的根因假设。

图1:rocprofv3 实测——MAIN dqdkdv 占 bwd 墙钟 87.6%（canonical；全配置 84–90%）、MfmaUtil 仅 9.9%（矩阵核闲 >80%）、MemUnitStalled 0.024%（非带宽瓶颈）、VGPR 124 无 spill。结论:加速的钥匙是砍 MAIN 浪费的迭代，不是带宽。

critique 证伪 scoping 自己的「grid starvation 根因」（数据驱动纠错）

scoping draft 最初把 grid starvation 列为头号根因:grid = (ceil(seqlen_kv/kN0), nhead, batch) = (16,8,2) = 256 workgroup 对 256 个 CU ≈ 1 block/CU，无第二波掩延迟；并以「16× 放大 grid → occupancy 3.39→6.96 waves（10.6→21.8%）、MfmaUtil 9.9→18.4%」佐证。但 critique 复测推翻了这个根因:

数据驱动纠错: critique 实测发现是 256× 超额订阅（grid 并不饥饿），真限制器是 per-block LDS/VGPR 上限卡住 waves/CU，不是 grid 数。⇒ B4 grid widening 依据作废、暂缓；本期聚焦 GetTileRangeAlongY 浪费（B2/B3）。同时修正 scoping 笔误:MemUnitStalled = 0.024%（非 2.4%）。
为什么这段值得讲: 它是一次诚实的自我证伪——团队自己提的根因（grid starvation）被自己的复测推翻，没有为了「实现一个酷候选」而硬上 B4。perf 工作最容易踩的坑就是「凭直觉优化没测准的瓶颈」。M8 的纪律是:scope 跟着数据走，证据不成立的候选就暂缓。

3  MI:计时基线为何「设备码 byte-identical」

measure 设施最大的风险是它本身改变了被测对象（观测者效应）。MI 的设计让 -perf 之外的一切——包括 253 套件——设备指令流逐位不变:计时只活在 host 包裹层。

hstu_attention_bwd_perf.hpp — time_op 唯一计时原语template <typename Fn> float time_op(bool measure, hipStream_t stream, Fn&& fn) { if(!measure) { fn(); return 0.f; } // 正常路/套件:只调一次 = 裸 launch // measure=true:cold3 warmup + nrep10 hipEvent gpu_timer,返回 per-launch 均值 ms ... warmup ...; ... record ...; return ms; }
机制 1
perf 字段纯 host
两个 bwd params 末尾追加 measure_perf + perf_{pre,memset,main,post}_ms，从不进 MakeKargs ⇒ 不入设备 kargs ⇒ 设备符号不变。
机制 2
dispatch 只包 host lambda
batched/group dispatch 把 PRE/memset/MAIN/POST 各 launch 包进 time_op（纯 host）；内层 MAIN 仍单发，warmup/repeat 由 time_op 做。launch 参数不变。
机制 3
-perf 在校验之后
harness -perf 块 gated 在 if(measure_perf) 且在梯度 FromDevice 之后 ⇒ 套件路完全不受扰，0 条 PERF 行污染。
byte-identical 的直接铁证（reviewer 自产 HEAD 基线复核）: mask-无关的 helper kernel（PRE dot_do_o / POST convert_dq / reduce_convert_dq）的 launch 现已走 time_op 包裹，但其设备码 6/6 逐位不变——这正是「host 包裹不碰设备码」最干净的证明。配套:FORWARD 9216/9216、BWD no_causal-NoLocal 256/256 identical;coder 口径 13782/13782（457 obj 全集，含 fwd）。套件 253/253，不给 -perf 时 0 条 PERF 行。
per-kernel 计时与 rocprofv3 互证（非臆造）: -perf 测得 canonical MAIN 0.263ms ≈ profile 266us、envelope 占 87% ≈ 87.6%、hd256 silu MAIN 0.971ms ≈ 943us;连「SiLU 26% 异常」都复现（silu/softmax = 1.27×，profile 335/266us）。两套独立测量互相印证 ⇒ 计时可信。

4  B2/B3 机制:从保守全扫收紧到真实 q-band

MAIN 是 KV-block-parallel:每个 KV-tile 沿 Q 维扫一串 Q-tile。GetTileRangeAlongY 返回该 KV-tile 需要扫的 [y_start, y_end)。pre-M8 它保守返回 全扫 (0,seqlen)——但 causal/window 下，大多数 Q-tile 对当前 KV-tile 零贡献。收紧 = 只扫真实有贡献的 q-band。

图2:同一 KV-tile 的 Q-扫描范围。全扫（左）把整列 Q-tile 都扫；B2（中）只扫 causal 三角带 y_start=align_down(i_x)；B3（右）只扫 window 窄带。收紧只少扫零贡献 tile——每个被访问 tile 内的 per-pixel IsTokenPairInsideMask 照旧掩，故唯一要求是范围必须是真实所需的 kM0-aligned superset。

hstu_block_masking.hpp — NoLocal causal 收紧（B2，self;cross 加 diff 偏移）// 收紧前:return {0, seqlen}; // 保守全扫 // 收紧后(causal):col c 只被 row≥c 的 Q attend ⇒ 该 KV-tile 最小列 i_x 决定 y_start y_start = (contextual_seqlen > 0 && i_x < max_uih_len) ? 0 // contextual 行 attend 全部 uih 列 → 不能漏 : align_down(i_x /* cross: −diff_q_kv_len */, YTile); // align_down 保证 ≤ 真实 min y_end = seqlen; // 安全上界;非 causal(含 P1-1 num_target)原样全扫
收紧必须覆盖的特例（漏一个就 silent-wrong）: (a) contextual 行 attend 全部 uih 列 → tile 触 uih 区时 y_start=0;(b) min_full 全 reach 行;(c) cross diff_q_kv_len 偏移;(d) 非 causal NoLocal 的 num_target 行不能排除（P1-1，故非 causal 原样全扫）。B3 的 window 带还要叠加 cross 偏移 + contextual + 非 causal min_full 行下沉（§5 校验器抓到的真 bug）。

5  离线穷举校验器（最大亮点）:在 GPU 跑之前抓到 2 个真 bug

收紧的失败模式是 numerically-wrong 但不崩溃:一个被错误排除的 q-tile 会永久丢掉它的 dK/dV/dQ 贡献，无任何报错。对拍可能因配置覆盖不全而漏。M8 的硬 gate 是一个离线穷举 superset 校验器——无需 GPU，穷举每个 (KV-tile, sq, sk) 验证收紧后的范围仍是真实所需的 superset。

校验器逻辑(test/validate_tile_range_y.cpp,与 GPU 同一组 make_hstu_* factory + 同 oracle): for 每个 (KV-tile i_x, 每个 q row sq, 每个 kv col sk): 若 oracle IsTokenPairInsideMask(sq,sk)=attend,但 sq 落在收紧 [y_start,y_end) 之外 ⇒ FAIL(收紧把真实有贡献的 q-row 漏了 = under-tighten) 穷举 self+cross × causal+非causal × 2 tile 形状(32×128 + 16×64) ⇒ 1,973,278 checks

校验器抓到的 2 个真 under-tighten bug（B3，被挡在 GPU 之外）

bug为什么对拍可能漏根因修法
① 非 causal + min_full需要「非causal × min_full × 特定行/tile」同时在场，对拍矩阵未必覆盖min_full 行（row_id≥max_id−mf）attend 所有列，在非 causal 下落在 band 下沿之下（物理起点 max_uih_len−mf），最初只在 y_end 处理 → 漏 y_start非 causal WithLocal 把 y_start 下沉到 max_uih_len−mf
② cross causal 大 diff + contextual需要「cross × 大 diff_q_kv_len × contextual」组合diff 大时 band 映射出界（y_end 被 clamp 到 0），但 contextual 行 [0,ctx) 仍 attend → 漏contextual 分支 floor y_end ≥ contextual_seqlen
修后:校验器 1,973,278 checks ALL GREEN。 这 2 个 bug 在任何 GPU 对拍之前就被穷举校验器抓到并修掉——离线穷举 gate 比对拍更早、更硬地挡住 under-tighten silent-wrong。

reverse-proof:证校验器「能判伪」（非 vacuous）

一个永远 GREEN 的校验器等于没校验。reviewer 在隔离副本上主动破坏收紧逻辑，看校验器是否变红:

破坏实验（reviewer，隔离副本非 git checkout）校验器结果报错
正常 M8 收紧ALL GREEN（1,973,278）—
破坏①:删 self causal NoLocal 的 contextual y_start=0 carve-outFAILKVtile@64 attends sq=0..5 but range=[64,128)
破坏②:删非 causal WithLocal 的 min_full y_start 下沉FAILnocausal,local mf=64: KVtile@64 attends sq=32.. but range=[48,128)
判伪成立: 两个破坏都让校验器 FAIL，且 FAIL 的正是 coder 声称它抓到的 2 类 bug ⇒ 校验器非 vacuous、确实在守 under-tighten。配合套件 253/253 + 那 2 个 bug 配置对拍 PASS + 大窗对拍，correctness 双重锁死。

诚实 Amdahl:实测 < [derived] 模型。 B2 实测 1.25–1.60× < draft [derived] ~1.9×:收紧只砍 MAIN 内 Q-tile 循环数，每 KV-block 的 K/V load、atomic dq_acc 写流量、kernel 启动开销不随之减半 → Amdahl 限制 < 2×。B3 实测 4.7–9.8× < [derived] ~22×:同理，且窄 window 时 MAIN 已降到与 PRE 同量级（window16 MAIN 0.032ms ≈ PRE 0.025ms），MAIN 不再压倒性主导，envelope 被 PRE/启动开销主导。实测多少记多少。
TFLOPS 是 tracking 不是 roofline: FLOPS 模型 = 5-GEMM（忽略 SiLU/softmax/dS elementwise），报的是 GEMM-only TFLOPS 作 tracking 指标，非硬件利用率;memset 单独计时不混入 MAIN（否则 MAIN TFLOPS 被人为拉低）。MAIN TFLOPS 随收紧上升:canonical softmax 163→212;window16 softmax 收紧后 1349.75。
