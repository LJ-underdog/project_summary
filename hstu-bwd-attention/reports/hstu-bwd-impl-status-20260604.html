HSTU Attention Backward — 实现现状（M0 脚手架 + M1 闸门）

这份文档忠实记录当前仓库里 HSTU 反向（bwd）GPU kernel 的真实代码：写了哪些文件、文件之间怎么 include / 依赖、运行时怎么一步步调用、哪些是直接复用 FMHA、哪些是新写 HSTU，以及现在能跑什么、还差什么。

读者：要 review 这套 bwd 实现的工程师（零基础友好，关键术语都配一句白话）
代码目录：ck_hstu/example/ck_tile/18_hstu_attention/  ·  主目标 gfx950 (MI350/CDNA4)  ·  落点 2026-06-04
TL;DR — 一句话现状

HSTU bwd 现状 = M0 脚手架（端到端编译/launch/对拍管线打通） + M1 闸门已通过：batched + SiLU + no-mask + bf16 + hdim64 + atomic 这一条最小路径已经端到端真实计算并对拍 PASS。结构上以 FMHA bwd 的 kr_ktr_vr（5 GEMM / 7 stage）为蓝本，HSTU 差异收敛到 MAIN pipeline 的两个 elementwise 段（SiLU / dsilu）和两个 scale（alpha / scale_p）。

M1 端到端对拍 PASS R1：FMHA default policy 零覆写复用 R2：VGPR 248 · AGPR 0 · Scratch 0 · occ 2

白话：M0 和 M1 分别交付了什么

  • M0（脚手架）：把「骨架」搭起来 —— params 结构、3-kernel 壳子、dispatch 模板、bf16 入口、对拍 harness、CMake target、instance 分支都建好；但 GPU bwd 的内核是把 dQ/dK/dV 全置 0 的占位。验收只要求「能编译、能 launch、对拍管线打通、打印三梯度误差」。
  • M1（闸门）：把占位换成真正的 SiLU MAIN pipeline。在放大梯度量级（attn_scale=1.0，梯度 ~5）下，GPU 算出的 dQ/dK/dV 与 CPU reference 数值对拍真 PASS（误差只到 bf16 舍入级，dK 逐位为 0）。两条设计期风险 R1（policy 能否零成本复用）/ R2（寄存器是否 spill / 掉 occupancy）都实测闭环。
「闸门」是什么意思？ M1 是整个方案最大的不确定点：能不能直接复用 FMHA 的寄存器/LDS 布局、加上 HSTU 多出来的 g 张量后会不会爆寄存器。M1 通过 = 这套「复用 FMHA + 收敛差异」的总策略被实测验证可行，后续 M2–M8 都是在这条已验证的路径上加功能。

当前能跑的唯一一条真实路径

batched（非 jagged/group） + SiLU（kUseSoftmax=false） + no-mask（causal=0） + bf16 + hdim_qk = hdim_v = 64 + atomic（kIsDeterministic=false）

其余轴目前都没真正实例化，但「拦截方式」并不一样：causal/softmax/deterministic 在 dispatch 里用编译期 if constexpr 门控成运行时 throw；jagged 与「非 hd64」是运行时 if 判断 + throw；group 则连 dispatch 入口都还没有（GroupBwdParams 仍是空 struct、harness 只跑 no-group）；fp16 是入口/harness 仅 bf16。详见 §8 覆盖面 vs TODO。

5  【图3】MAIN pipeline 七阶段（当前 SiLU 路）

一个 block 固定一块 K/V（KV-resident），循环吃 Q tile，跑 5 个 GEMM + 两段 elementwise。clay 高亮 = HSTU 相对 FMHA 的改写点；其余阶段（5 个 GEMM 的形状 / LDS / shuffle）原样复用 FMHA default policy。当前只实现 SiLU 路，softmax 路（STAGE2 不算 dsilu、STAGE5 改 ds=p·(dp−D)）是 M5 TODO。

图3：5 个 GEMM（STAGE1/3/4/6/7）+ 两段 elementwise（STAGE2/5）。三处 clay 高亮 = HSTU 改写点：STAGE2（alpha + silu/dsilu）、STAGE5（ds = dp·g）、收尾（dQ/dK ×alpha、dV 不乘）。

代码佐证（pipeline 主体，已删节）

// STAGE 2, HSTU SiLU: s = alpha*S; p = silu(s)*scale_p; g = scale_p*dsilu(s) const CompDataType s = alpha * type_convert<CompDataType>(s_acc[i_j_idx]); const CompDataType sig = f_sigmoid(s); // rcpf(1+expf(-x)) const CompDataType silu = s * sig; const CompDataType dsilu = sig * (1.f + s * (1.f - sig)); p(i_j_idx) = silu * scale_p; // → dV g(i_j_idx) = scale_p * dsilu; // → dS // ... // STAGE 5, dS = dP * g (g already carries scale_p) ds(i_j_idx) = dp_acc[i_j_idx] * g[i_j_idx]; // ... // 收尾 tile_elementwise_inout([&alpha](auto& x){ x = x * alpha; }, dq_acc); // dQ ×alpha if constexpr(kIsDeterministic) store_tile(dq_dram_window, dq_acc); else update_tile(dq_dram_window, dq_acc); // atomic_add tile_elementwise_inout([&alpha](auto& x){ x = x * alpha; }, dk_acc); // dK ×alpha；dV 不乘

源：hstu_attention_no_softmax_bwd_pipeline.hpp（STAGE2 ~L395、STAGE5 ~L442、收尾 ~L494/L512）。

6  复用 FMHA vs 新写 HSTU

这套实现的总策略：能 include 复用就复用，把差异收敛到尽量小。下面把两边摊开。

复用 · 直接 include
FMHA default policy
BlockFmhaBwdPipelineDefaultPolicy —— 5 个 GEMM 形状 + 所有 LDS / shuffle 描述子，零覆写。
复用 · 直接 include
mask / epilogue / dropout
GenericAttentionMask<false>（平凡 no-mask）、Default2DEpilogue（写 dk/dv）、BlockDropoutBwd<false,...>。
复用 · 直接 include
problem / shape / enum
BlockFmhaBwdPipelineProblem、TileFmhaBwdShape、BlockAttentionBiasEnum（保留 NO_BIAS + dummy BiasDataType，让 policy 编译）。
新写 · HSTU
SiLU MAIN pipeline
no_softmax_bwd_pipeline.hpp —— 以 FMHA kr_ktr_vr 为蓝本改写（不直接 include），插入 STAGE2/5 两段 elementwise。
新写 · HSTU
MAIN kernel + POST
bwd_kernel.hpp —— 自写 kernel 携带 alpha+scale_p 两个标量；POST convert_dq_kernel 把 float dq_acc cast 成 bf16。
新写 · HSTU
params / dispatch / 入口 / harness
bwd_params.hpp、batched_backward_dispatch.hpp、no_group_backward_bf16.cpp、example_hstu_attention_bwd.cpp。
为什么 pipeline 是「改写」而不是「include 复用」？ FMHA 的 kr_ktr_vr pipeline 内部写死了 softmax 的 LSE/D load 和单一 scale；HSTU 要在 GEMM 之间插 silu/dsilu 并携带两个 scale，无法用模板参数注入，所以以它为结构蓝本逐段重写。但所有 policy 描述子和 5 个 GEMM 仍原样调用 —— 这正是 R1（policy 零覆写复用）能闭环的原因。

7  关键工程决策（来自 M1 报告）

决策 ①
目标 ck_tile 是 ck_hstu 自带的较新版
ck_hstu/include/ck_tile 的 FMHA bwd 接口与 /root/ck 不同（Traits/Shape/Problem 签名、kUseTrLoad、smem 在首参）。已全部对齐到 ck_hstu 版本。
决策 ②
自写 kernel（不复用 FMHA kernel）
FMHA bwd kernel 只传单一 raw_scale（且 scale=raw_scale·log2e），塞不下 HSTU 需要的 alpha + scale_p 两个标量 → 必须自写 kernel 层。
决策 ③
float dq_acc + atomic + POST convert
dQ 输出是 bf16，但累加要 float 精度且多 block 写同一行 → 用 float dq_acc + atomic_add 累加，再 POST 逐元素 cast 回 bf16（atomic 路 nsplits=1，dq_acc 与 dq 同布局，convert 纯 elementwise）。
决策 ④
保留 BiasEnum=NO_BIAS dummy
为复用 default policy，problem 仍带 BiasEnum=NO_BIAS + dummy BiasDataType/LSEDataType/DDataType；SiLU 路从不读写这些段（LDS 里仍预留，trim 是 R6 perf TODO）。
R1 / R2 设计期闸门已闭环： R1 = FMHA default policy 直接复用、零覆写（pipeline 原样调全部 Make*/Get* + 5 GEMM，GEMM 间插 dsilu 与中间 reg 分布兼容）。R2（CDNA4 占用模型）实测：VGPR=248 · AGPR=0 · ScratchSize=0（无 spill） · occupancy=2 waves/SIMD —— 留 g 张量未致 spill、未掉 wave。

9  验证现状（数值 + 资源）

对拍 oracle = CPU reference

金标准是 reference_hstu_attention_bwd.hpp 里的 855 行 CPU 实现：逐 batch/head 重算 S→P，再按 6 步推导出 dV / dP / dS / dQ / dK（SiLU 路 dS = dP·scale_p·dsilu(S)）。GPU 三张量与之逐元素比对。

M1 数值结果（attn_scale=1.0，梯度量级 ~5）

dQ: max_abs_err=0.00012207 mean_abs_err=3.7e-09 (max|ref|=5.125) dK: max_abs_err=0 mean_abs_err=0 (max|ref|=5.21875) dV: max_abs_err=0.00390625 mean_abs_err=2.9e-07 (max|ref|=4.625) [PASS] dQ [PASS] dK [PASS] dV

误差只到 bf16 舍入级，远小于阈值（rtol≤2e-2 / atol≤5e-2），dK 逐位为 0。非巧合：在真实量级 ~5 的梯度下三者皆 PASS（M0 默认 case 因 scale_p≈1/134 梯度极小、落在阈值内才 PASS，那不算数值正确）。

稳定性（6/6 PASS，exit 0）

  • 默认 attn_scale（scale_p=1/max_seqlen_q）
  • b4 × nhead8 × seq256、b1 × nhead1 × seq512
  • seq200（非 kN0=128 整除）、seq130（非 kM0=32 整除 → 验 OOB 由 buffer_load 归零）

来自 amdclang++ -Rpass-analysis=kernel-resource-usage。CDNA4 加法占用模型：ArchVGPR+AGPR = 248+0 → 512/248 ≈ 2 waves。AGPR=0（MFMA 累加器落统一 VGPR 池），R2 设计期担忧的「留 g 叠加 AGPR 累加器」最坏情形本构型未出现。LDS 32768 B（含未用 LSE/D/bias 段，R6 可省）。

10  如何构建 / 运行（复现）

构建

# 在 ck_hstu 仓库根目录 cmake -B build -DBUILD_DEV=OFF -DGPU_TARGETS=gfx950 cmake --build build --target tile_example_hstu_attention_bwd -j$(nproc)

target 是 EXCLUDE_FROM_ALL，必须显式 --build --target。gfx95 上 CMake 自动加 -fno-slp-vectorize -DBUILD_HSTU_FOR_GFX95_ONLY -DCK_TILE_FLOAT_TO_BFLOAT16_DEFAULT=3。bwd target 还会一并编 fwd bf16 entry + instances/*forward_bf16*.cpp（harness 要先跑 GPU fwd 产 O）。

运行（M1 闸门 case）

./build/bin/tile_example_hstu_attention_bwd \ -prec=bf16 -b=2 -nhead=2 -hdim_qk=64 -hdim_v=64 \ -seqlens=128 -softmax=0 -causal=0 -attn_scale=1.0 -v=1
务必带 -attn_scale=1.0：把梯度量级放大到 ~5，才能真正检验数值正确（否则默认 scale_p≈1/134 梯度太小，PASS 不能区分「真对」和「输出近 0」）。

常用开关：-b batch、-nhead 头数、-seqlens 序列长、-v=1 开 CPU 对拍、-dump_grad=1 dump device/ref 梯度到 .dat。注意 -softmax/-causal/-deterministic 非 0 会触发对应里程碑的 throw（尚未实现）。
