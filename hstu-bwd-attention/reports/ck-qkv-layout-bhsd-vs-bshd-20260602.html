bhsd vs bshd：QKV 在显存里到底怎么排，为什么要两种都支持

同一份 Q/K/V 张量，在 HBM（显存）里有两种摆法。本文从"什么是内存布局 / stride"讲起，一路讲到 ck FMHA 用一个 iperm 开关、零成本支持两种布局，以及为什么 HSTU 必须锁死其中一种。

适合：几乎没有 GPU kernel / 内存布局基础，但想看懂这块代码的工程师
预估阅读 ~25 分钟  ·  配色约定：clay = bhsd / FMHA 默认   olive = bshd / HSTU  ·  2026-06-02
TL;DR

一个逻辑上 4 维的张量 [B,H,S,D]，在显存里其实是一条直线。"布局"就是决定这条直线上谁先排、谁后排。bhsd = 先按 head 排（同一个 head 的整条序列连续）；bshd = 先按 token 排（同一个 token 的所有 head 连续）。

ck 的 FMHA kernel 不在乎布局——它只读一组 stride（步长）数字，按 stride 去显存里取数。换布局 = 换几个 stride 数字，同一份编译产物就能跑两种，成本≈0。

之所以两种都留：框架（PyTorch / flash-attn）吐出来的天然是 bshd，varlen 打包也只能 bshd（这是 HSTU 锁死 bshd 的原因）；而 bhsd 在稠密单 head 场景访存最规整，所以留作 example 默认。两种都支持，调用方按自己数据所在的布局挑，谁都不用做昂贵的 transpose。

1. 先建立直觉：什么是"内存布局 / stride"

在碰 bhsd / bshd 这些字母之前，得先有一个画面：多维张量在显存里到底长什么样。

1.1 显存是一条直线，张量是我们脑补的形状

我们写代码时把 Q 想成一个 4 维方块 [B, H, S, D]：B 个 batch、每个 batch 有 H 个注意力头（head）、每个 head 有 S 个 token（序列位置）、每个 token 是一个 D 维向量。但 显存（HBM）本身没有"维度"——它就是一长条编了号的格子：0 号、1 号、2 号…… 每格放一个数。

所谓"内存布局"，就是我们约定：把这个 4 维方块里的每个元素，按什么顺序塞进这条直线。换句话说——先按哪个轴走、再按哪个轴走。逻辑内容完全一样，只是物理摆放顺序不同。

类比 · 图书馆排书
同一批书（= 同一个张量），上架方式可以不同：
· 按作者分区：同一个作者的所有书排成连续一段，找"某作者的全部作品"超快，但找"所有书里书名叫《X》的"就得满馆跑。
· 按主题分区：同一主题下不同作者的书挨在一起，找"这个主题"快，找"某作者全集"就分散了。
书没变，查找的连续性变了。布局就是这件事：你把谁排成连续的一段，取那一类数据时就快。

1.2 stride（步长）：在某个轴上走一格，地址要跳多远

stride（步长）是描述布局的数字。定义很朴素：在某个轴上前进一格，线性地址要跳过多少个元素。

举例：如果一个 token 的向量是 D=128 维、且这 128 个数在显存里连续摆放，那么 D 轴的 stride 就是 1（走到同一 token 的下一维，地址 +1）。而"走到下一个 token"要跳过整整一个 token 的 128 个数，所以 token 轴（即 seq 轴）的 stride 就是 128。同一份数据，换个摆法，这些 stride 数字就变了——这正是 bhsd 与 bshd 的全部区别所在（第 4 节会精确给出）。

记住这一句：取数地址 = 基地址 + b×batch_stride + h×nhead_stride + s×stride + d×1。布局变的只是这几个 stride 的取值，公式形状不变。最内层（D 维）的 stride 恒为 1（行内连续），这点两种布局都一样。

2. bhsd 与 bshd 的定义

四个字母就是四个轴的排列顺序，从外到内书写。"外层"= 排得最稀疏、跨度最大的轴；"内层"= 挨得最紧、连续的轴。

bhsd · head-major
[B, H, S, D]
head 排在 seq 前面。固定一个 head，它名下整条序列 S×D 是连续的一大块。这是 ck FMHA example 的默认（iperm=1）。
bshd · token-major
[B, S, H, D]
seq 排在 head 前面。固定一个 token，它的所有 head H×D 挨在一起；相邻 token 之间隔着"全部 head"。这是框架 / HSTU 的天然布局（iperm=0）。

2.1 代码里的开关：一个 iperm 搞定

ck 的 FMHA example 用命令行参数 iperm 切换输入布局。源码（fmha_bwd.cpp:55-58）：

// fmha_bwd.cpp create_args() (line 55-58) .insert("iperm", "1", // <-- 默认 "1" "permute input\n" "if true, will be b*h*s*d, else b*s*h*d")

这个 bool 一路传到决定张量形状的小函数 get_lengths（fmha_bwd.cpp:269-278）——它就是"按 permute 决定四个轴怎么排"的本体：

// fmha_bwd.cpp get_lengths (line 269-278) auto get_lengths = [&](bool permute, index_t b, index_t h, index_t s, index_t d) { if(permute) return std::array<index_t, 4>{b, h, s, d}; // bhsd else return std::array<index_t, 4>{b, s, h, d}; // bshd };

连打印出来的布局名都直接由它决定（fmha_bwd.cpp:406-408）：permute ? "bhsd" : "bshd"。

已核实：本文所有行号与 stride 公式均已对照 /root/ck 实际源码逐条复核（2026-06-02），与上述位置一致。

两句话总结这张图：

bhsd 看到什么
固定一个 head，它的 S×D 整块连续。"取某个 head 的整条序列"= 顺着读一大段，连续性最好。
bshd 看到什么
固定一个 token，它的 H×D 连续。"取某个 token 跨所有 head 的全部特征"= 顺着读一段；但同一个 head 的相邻 token 之间隔了一整圈 head。

4. 差异本质：同一个 kernel，只是 stride 不同

这一节是理解"为什么支持两种布局几乎不要钱"的关键：kernel 代码根本不知道什么叫 bhsd / bshd，它只认 stride。

4.1 kernel 只存 stride，按 stride 构造视图

FMHA bwd 的 kernel 参数结构体（kargs）里，关于 Q 的布局信息只有三个数：stride_q（沿 seq 轴）、nhead_stride_q（沿 head 轴）、batch_stride_q（沿 batch 轴）。见 fmha_bwd_kernel.hpp:145 / 153 / 276。kernel 拿这几个数去 make_naive_tensor_view 构造一个"显存视图"，之后所有访问都走这个视图（fmha_bwd_kernel.hpp:1215-1218）：

// fmha_bwd_kernel.hpp (line 1215-1218) 构造 Q 在显存中的视图 auto q_dram_naive = make_naive_tensor_view<global>( q_ptr, make_tuple(kargs.seqlen_q, kargs.hdim_q), // 逻辑形状 [S, D] make_tuple(kargs.stride_q, 1), // 步长：seq 轴=stride_q，D 轴=1 ...);

看最后一行：D 轴步长恒为 1（行内连续），seq 轴步长是变量 stride_q。布局的全部差异，就藏在喂进来的 stride_q / nhead_stride_q 取什么值。kernel 二进制一个字节都不用改。

4.2 Q 的 stride 对照表

这些 stride 在 host 侧按 i_perm 算好再传给 kernel（fmha_bwd.cpp:448 / 459 / 470，已逐行核对）：

步长（含义） bhsd (iperm=1) bshd (iperm=0)
stride_q
相邻 token		hdim_qnhead * hdim_q
nhead_stride_q
相邻 head		shape_seqlen_q * hdim_qhdim_q

// fmha_bwd.cpp 原文 (line 448, 459, 470) const index_t stride_q = (i_perm ? hdim_q : nhead * hdim_q); const index_t nhead_stride_q = (i_perm ? shape_seqlen_q * hdim_q : hdim_q); const index_t batch_stride_q = (nhead * shape_seqlen_q * hdim_q); // 不含 i_perm！

注：表里 shape_seqlen_q 就是源码里那个序列长度变量 — batch 模式下它等于 seqlen_q，jagged/变长模式下它是打包后的总 token 数；这里照搬源码命名以便对照。把这张表读透，整件事就通了：

精髓：bhsd ↔ bshd 的全部区别，就是把那个"小步长 hdim_q"挂在 seq 轴还是 head 轴上——
· bhsd：小步长给 seq（相邻 token 只隔 hdim_q）⇒ 同 head 整段连续。
· bshd：小步长给 head（相邻 head 只隔 hdim_q）⇒ 同 token 整段连续。
而 batch_stride_q 两种布局完全相同，因为 batch 永远是最外层、最稀疏的轴。所以支持两种布局 = 纯 stride 算术，没有分支化 kernel、没有第二份编译产物。

5. 使用差异 → 访存连续性与性能

既然结果一样、kernel 一样，那两种布局到底差在哪？差在 GPU 取数时的连续性——也就是访存效率。

5.1 bwd 怎么切活

FMHA bwd 的 grid（GPU 把活分给一堆 workgroup 的方式）按 (seqlen_k 块, nhead, batch) 三维切（fmha_bwd_kernel.hpp:1063-1068）— 注意切的是 K/V 那条序列轴（seqlen_k），因为反向是 K/V-centric 的。每个 workgroup 固定一个 (batch, head) 并认领一个 K/V 块，块内再沿 seqlen_q 以 stride_q 一片一片（tile）地把 Q 搬进片上内存，逐步累加出这个块的 dK / dV。

白话："合并访存"（coalescing）是 GPU 的省钱关键：一个 warp 的 32 个线程如果去读连续的一段地址，硬件一次就能合并成少数几笔内存事务；如果地址东一块西一块（strided），就得拆成多笔，带宽浪费、还更吃 L2 / 预取。布局影响的就是这个连续性。

5.2 两种布局下的访存形态

bhsd
最规整
固定 head 时，seq×hdim 是连续的一整块。tile 加载即使跨行也连续 → 合并访存最干净、tiling 最规整。对稠密单 head attention 最友好。
bshd
行内仍连续，行间跳跃
固定 head 时，相邻 token 之间要跳 nhead×hdim（strided）。但每个 token 自己那段最内层 hdim 仍然连续 → 每一行内部照样合并，受影响的只是行与行之间的 L2 局部性 / 预取效率。
诚实说：实际性能差距通常不大。因为 hdim 一般是 64 或 128，单是这一段连续就足够触发合并访存了；行间跳跃对现代 GPU 的 cache / 预取来说不是大问题。所以这更多是"哪种更省心 / 更匹配数据来源"的工程权衡，而非数量级差异。bhsd 在稠密场景最省心，这是 example 把它设为默认（iperm=1）的原因。

6. 为什么两种都要支持

既然 kernel 不在乎、性能差距也不大，为什么不只留一种？因为"数据从哪来"由不得 kernel 决定，而做一次布局转换（transpose）很贵。

理由 1 · 零拷贝对接框架
框架吐出来天然是 bshd
PyTorch / flash-attn / vLLM 的 Q/K/V 是 nn.Linear 投影后 reshape 得到的，天然就是 [B,S,H,D]（token-major）。若 ck 只收 bhsd，每次调用都要先把 Q/K/V 整份从 HBM 读出、transpose、再写回 HBM——一趟昂贵的全量搬运。支持 bshd = kernel 直接吃原始内存，省掉这趟 transpose。
理由 2 · varlen / jagged 打包
变长序列只能 bshd
把一批变长序列沿 seq 轴首尾拼成一条 [1, ΣL, H, D]（省掉 padding），要求 seq 轴紧挨 batch 轴 → head 必须排在 seq 之后。这天然就是 bshd。这正是 HSTU 锁死 bshd 的根因（下方详述）。
理由 3 · bhsd 留作默认
匹配习惯 + tiling 更连续
部分训练框架 / 老代码习惯 head-major；稠密 GEMM 在 bhsd 下 tiling 更连续（见第 5 节）。所以 example 默认 iperm=1。
理由 4 · 代价≈0
两种全留，没负担
既然区别只是几个 stride 数字（第 4 节），两种全留几乎不增加代码 / 二进制成本。调用方按自己数据所在的布局挑一个，谁都不用做 transpose。

6.1 HSTU 为什么没有 iperm 开关

HSTU 面向推荐场景，输入就是 varlen 打包的序列，所以它从张量命名上就锁死了 bshd。看 reference 实现的函数签名（reference_hstu_attention_bwd.hpp:66-74）——每个张量都叫 *_batch_seq_nhead_hdim，没有任何 permute 选项：

// reference_hstu_attention_bwd.hpp (line 66-74) const HostTensor<T>& q_batch_seq_nhead_hdim, // [B, S, H, D] 写死 const HostTensor<T>& k_batch_seq_nhead_hdim, const HostTensor<T>& v_batch_seq_nhead_hdim, ... HostTensor<T>& dq_batch_seq_nhead_hdim,

访问时永远是 (0, seq_offset + s, i_head, k) 这种 (b, s, h, d) 顺序的下标（reference_hstu_attention_bwd.hpp:438 / 473 / 482 等），且 jagged 模式断言 batch 维 == 1（:91-95）——正是 [1, ΣL, H, D] 打包形态。HSTU 没有、也不需要 iperm：它的世界里只有 bshd。

7. 别混淆：V 的 is_v_rowmajor 是另一条正交轴

iperm 管的是 b / h / s 三个轴的先后顺序（也就是本文主题 bhsd vs bshd）。而 V 张量另有一个独立开关 is_v_rowmajor（fmha_fwd.cpp:587, 874-880），管的是 V 最末两维要不要转置存：

· row-major：[…, seqlen_k, hdim_v]（正常摆）
· col-major：[…, hdim_v, seqlen_k]（即 Vᵀ 预先转置好）

为什么需要它：attention 的第二个 GEMM 用的是 Vᵀ（fwd 的 O = P·V、bwd 的 dP = dO·Vᵀ）。若 V 在显存里就已经按转置摆好，kernel 内部就省掉一次转置。

关键：这两个开关正交，可任意组合（bhsd + V row-major、bshd + V col-major……都合法）。本文只讲 iperm；遇到 V 的转置问题，记住那是另一条轴即可，别和 bhsd/bshd 搅在一起。

8. 小结 & 常见疑问

一句话回顾

张量在显存里是直线；布局 = 排列顺序；stride = 每个轴走一格跳多远。bhsd（head-major，clay，FMHA 默认）让同 head 整条序列连续；bshd（token-major，olive，框架 / HSTU 天然）让同 token 所有 head 连续。kernel 只认 stride，换布局只是换几个数字、同一份二进制就能跑，所以两种全留——让调用方按数据来源挑，避免昂贵的 transpose。

布局不同，算出来的结果会不一样吗？
不会。布局只改变数据在显存里的摆放顺序与读取地址，参与运算的数值完全相同，梯度 dQ/dK/dV 数值一致（只是同样按对应布局摆放写回）。它是纯访存层面的差异，不是算法差异。
那我到底该选哪个？
看你的数据已经是哪种布局，就用哪种，避免无谓的 transpose。来自 PyTorch / flash-attn / vLLM 投影 → 用 iperm=0（bshd）；变长序列打包 → 只能 bshd；自己造的稠密单 head 数据、或想要最规整 tiling → iperm=1（bhsd）。
支持两种布局是不是要编译两份 kernel？
不用。同一份编译产物。差异全在 host 侧算好的 stride_q / nhead_stride_q 等数字里（见第 4 节对照表），kernel 通过 make_naive_tensor_view(stride) 按 stride 取数，代码不分叉。
为什么 batch_stride 两种布局一样？
因为 batch 永远是最外层、最稀疏的轴——不管内部 h/s 怎么排，一个完整 batch 总是 nhead×seqlen×hdim 个元素。bhsd↔bshd 的差异只发生在 batch 内部的 h 与 s 谁先谁后，所以跨 batch 的步长不变。
性能差距大吗？要不要为此纠结？
通常不大。hdim（64/128）那段连续已足够触发合并访存；bshd 只是行间跳跃、影响 L2 局部性。除非你在做极致调优，否则优先按"数据本来是什么布局"来选，省掉 transpose 带来的收益远大于布局本身的微小差异。
is_v_rowmajor 和 bhsd/bshd 是一回事吗？
不是。iperm（bhsd/bshd）管 b/h/s 的顺序；is_v_rowmajor 管 V 末两维 (seq, hdim) 要不要转置存，服务于第二个 GEMM 用 Vᵀ。两者正交、可任意组合（第 7 节）。
