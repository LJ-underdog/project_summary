反向主 pipeline 的 5 个 Block GEMM 深入对比

标准 FMHA backward 主 kernel（pipeline 变体 kr_ktr_vr）的热循环里有 5 颗矩阵乘。它们到底谁乘谁、产出什么、被消掉哪根轴、有何不同——本文用一把统一的尺子逐个量。

适合：想真正搞清这 5 个 GEMM 输入/输出/收缩维区别的 kernel 工程师
预估阅读：通读 ~20 分钟  ·  对照源码 ~1 小时  ·  2026-06-02  ·  源文件 block_fmha_bwd_dq_dk_dv_pipeline_kr_ktr_vr.hpp
TL;DR

这 5 颗 GEMM 就是反向计算的骨架。按产物分两类：2 颗产「分数」（gemm_0→S、gemm_2→dP，输出都是 query×key 的方阵）；3 颗产「梯度」（gemm_1→dV、gemm_3→dK、gemm_4→dQ，输出都带头维）。

真正区分它们的是「收缩维」——被求和消掉的那根轴：gemm_0/2 沿头维（d_qk / d_v）求和 → 得分数矩阵；gemm_1/3 沿 query 轴(kM0) 求和 → dV/dK 是"对所有 query 累加"，所以用常驻寄存器累加器；gemm_4 沿 key 轴(kN0) 求和 → dQ 反过来"对所有 key 累加"，需要 atomic / split-workspace。收缩轴一旦看懂，累加方式与显存写法就全都解释通了。

1. 一把统一的尺子：C[M,N] = A[M,K] · B[K,N]

任何矩阵乘都能拆成三个角色。把这把尺子记牢，后面 5 个 GEMM 全都照它套。

  • 输出空间 M×N：结果矩阵的两根维度，决定"这颗 GEMM 产出长什么样"。
  • 收缩维 K（contraction dim）：两个输入共享、并在乘加中被求和消掉的那根轴。白话：沿 K 把一串乘积加起来，K 就"消失"了。
  • 两个输入操作数 A[M,K] / B[K,N]：各自一头连着输出维(M 或 N)，另一头连着收缩维 K。

图1 · 统一心智模型：每颗 GEMM 都有「输出空间 M×N」「收缩维 K」「两个操作数」三个角色。下文 5 个 GEMM 全部用它来量。

怎么用这把尺子？看一颗 GEMM，先问三句：① 输出 C 是什么形状（M×N）？② 哪根轴被消掉了（K）？③ 两个输入分别从哪来（常驻寄存器 / LDS / 寄存器重分布）？答完这三问，这颗 GEMM 就吃透了。

3. 四个维度看「区别」

同样是矩阵乘，这 5 颗的差异集中在四件事上：输出空间、收缩轴、是否累加、操作数转置来源。逐个拆。

3.1 区别一：输出空间不同（分数空间 vs 头空间）

看输出 C 的两根维度——是 query×key 的方阵，还是带头维的梯度。

图2 · 五个 GEMM 的 [A]·[B]=[C] 形状并排，按输出空间着色：橙=分数空间(S/dP)，绿=头空间(dV/dK/dQ)。右侧标各自收缩维。注意 viewBox 顶部为图例。

读图法：每行是一颗 GEMM 的 A · B = C，方框下方小字是该张量形状。C 的颜色 = 输出空间——橙 = query×key 方阵（分数 S/dP），绿 = 带头维的梯度（dV/dK/dQ）；行右端橙字标出被求和消掉的收缩维。一眼可见：上两行（gemm_0/2）消掉头维 → 留下方阵；下三行（gemm_1/3/4）消掉序列轴 → 留下梯度。

3.2 区别二：收缩轴不同（这正好解释了"归约轴"）

被求和消掉的那根轴，决定了梯度"对谁求和"，也直接决定了累加方式与显存写法。三组：

图3 · 收缩轴三分组：头维(d_qk/d_v) 产分数；query 轴(kM0) 产 dV/dK 用常驻累加；key 轴(kN0) 产 dQ 需 atomic/split-workspace。

3.3 区别三：累加 vs 新鲜

累加器（常驻）
gemm_1 / gemm_3
输出 dv_acc / dk_acc 跨整个 Q 内循环活在寄存器里，每个 Q tile 把贡献加进去，循环结束一次写出。因为本 workgroup 独占这个 KV 块、扫遍所有 query，无需 atomic。
每轮新鲜
gemm_0 / gemm_2
输出 s_acc / dp_acc 是中间量，每个 Q tile 重新算一份，用完即弃，不跨轮存活。
每轮写回
gemm_4
dq_acc 每轮清零、本轮算完即写回 HBM。但 dQ 全局是"对所有 KV 块求和"，故写回须 atomic 或 split-workspace。

3.4 区别四：操作数转置来源不同（经 LDS vs 纯寄存器）

需要转置操作数的 GEMM，转置怎么来？这里有两条必须分清的路：

GEMM需转置的操作数转置怎么来另一操作数
gemm_1Pᵀ（A 操作数）纯寄存器重分布（PTFromGemm0CToGemm1A，line 643）—— P 已在寄存器，重排 lane/分布即可，不经 LDSdO：LDS→reg（流式）
gemm_3dSᵀ（A 操作数）纯寄存器重分布（SGradTFromGemm2CToGemm3A，line 704）—— dS 已在寄存器，不经 LDSQᵀ：经 LDS shuffle（循环顶部 503-504 备好）
gemm_0Kᵀ（B 操作数）常驻寄存器（hot loop 前 Reg→LDS→Reg shuffle 转置好，整循环复用）Q：LDS→reg（流式）
gemm_2Vᵀ（B 操作数）常驻寄存器（V 直接载入，由 policy 处理布局）dO：LDS→reg（流式）
gemm_4Kᵀ（B 操作数）常驻寄存器（同 gemm_0 的 Kᵀ，按 kK4 切片复用）dS：LDS→reg（STAGE 6 存 LDS，STAGE 7 分块读）
务必别混的两类：① Pᵀ / dSᵀ 走 纯寄存器重分布——数据本就在寄存器，只是换 lane 映射，零 LDS 往返；② Qᵀ / dOᵀ / Kᵀ 走 LDS shuffle——必须写进共享内存、按转置布局再读回。前者快（省一次 LDS round-trip），是 CK 把"刚算出来的中间结果"喂给下一颗 GEMM 的关键技巧。

4. 与主篇 / 归约轴的联系

这 5 颗 GEMM 的收缩轴差异，直接解释了主 pipeline 的两个核心设计。

为什么 KV 外、Q 内
dV/dK 沿 query 归约
gemm_1/gemm_3 沿 kM0(queries) 求和 → dV/dK 是"固定一个 key、把所有 query 的贡献加起来"。把 KV 块固定在外层、Q 在内层流式扫最自然，dv_acc/dk_acc 就能常驻寄存器逐轮累加。
为什么 dQ 特殊
dQ 沿 key 归约
gemm_4 沿 kN0(keys) 求和 → dQ 是"固定一个 query、把所有 key 的贡献加起来"。但 key 被切到不同 workgroup，同一行 dQ 被多个 workgroup 写 → 必须 atomic 或 split-workspace。这正是 STAGE 7 两条写回路的由来。
为什么先 S/dP 再梯度
2 产分数 + 3 产梯度
gemm_0/2 沿头维归约先得到 S / dP（分数空间），softmax 反向用它们算出 dS，再由 gemm_1/3/4 沿序列轴归约产出三个梯度。分数空间是梯度空间的"前置原料"。
想看这 5 颗 GEMM 如何嵌进完整的 7 阶段热循环（含 softmax 还原 P、dS=P⊙(dP−D)、显存搬运与转置细节）→ 见姊妹篇 反向主 pipeline · 七阶段逐阶段拆解。本文是它的"GEMM 放大镜"。想搞清这些 GEMM 的输入（Q/K/V/dO/LSE/D）各自从哪来、谁是 fwd 存盘的 → 见 反向所需的保存张量。

5. 落到硬件：这些 GEMM 在 GPU 上怎么算

前面把 5 颗 GEMM 当成抽象的 A·B=C。这一节把它们接到 AMD CDNA（gfx942=MI300 / gfx950 一类）的真实硬件上——它们不是标量三重循环，而是由矩阵核心上的 MFMA 指令成块算出来的。看懂这层，前文的"常驻寄存器""寄存器重分布转置"才真正落地。

5.1 矩阵核心与 MFMA 指令

每颗 Block GEMM 最终都由 WarpGemmMfmaDispatcher 挑出一条 MFMA（Matrix Fused Multiply-Add，矩阵乘加）硬件指令来发射（policy 里 5 颗 GEMM 各选一条：GetQKBlockGemm/GetPTOGradTBlockGemm/GetOGradVBlockGemm/GetSGradTQTBlockGemm/GetSGradKTBlockGemm = line 32 / 66 / 104 / 138 / 176）。一条 MFMA 一次算的是一个小矩阵块的乘加，而不是一个标量——这是矩阵核心（matrix core，类比 NVIDIA 的 tensor core）的本事。dispatcher 为 f16 输入 / f32 累加列出的可选形状（warp_gemm_dispatcher.hpp:40-57，记作 M×N×K；注意同文件 line 36 的 16×16×16 是 fp32 输入那条，与此处 line 56 的 f16 16×16×16〔v_mfma_f32_16x16x16_f16〕是两条不同指令，勿混）：

CDNA3 (gfx942 / MI300，本篇主目标)： 32×32×8 16×16×16 ← 原生 f16 MFMA，累加 f32 CDNA4 (gfx950 / MI350，新增)： 32×32×16 16×16×32 ← K 翻倍 → 2× 吞吐 dispatcher 其它形状： 4×64×16 64×4×16 （CK warp 形状，按目标芯片映射）
务必按代区分：32×32×8 与 16×16×16 是 CDNA3(gfx942) 原生的 f16 MFMA；32×32×16 / 16×16×32 是 CDNA4(gfx950) 才新增的"K 翻倍"形状（2× 吞吐），在 MI300 上并不可用——dispatcher 按编译目标芯片选取。所有 f16 MFMA 的累加恒为 FP32。注意：MFMA 是 CDNA3/CDNA4 专有指令，到 CDNA5(MI400) 已整体移除、改用 WMMA；本篇只讨论 gfx942/gfx950。
一条 MFMA 把 A 的 M×K 小块 × B 的 K×N 小块，累加进 C 的 M×N 小块（即 D=A·B+C）。可一颗 Block GEMM 的整块 kM0×kN0（动辄上百）远大于一条 MFMA 的 16/32，所以必须靠"多 warp，每 warp 再发多条 MFMA"把整块铺满。

第 1 层 · Block
Block tile（kM0×kN0）

5.3 wavefront = 64 lane

AMD 的一个 warp 叫 wavefront（波前），含 64 个 lane（通道，即单个线程；见术语速查）——get_warp_size() 返回 HIP 的 warpSize（arch.hpp:51），在 CDNA3/4（gfx942/gfx950）上即 64（wave64；对比 NVIDIA 的 32。注：CDNA5/MI400 改用 wave32）。一条 MFMA 由整个 64-lane wavefront 协作完成：操作数被切片分摊到 64 个 lane 的私有寄存器，算完后 C 结果也按一种固定模式散布在这 64 个 lane 的寄存器里——没有哪个 lane 单独握有完整的一行或一列。记住这一点，下一节的"布局转置"才讲得通。

5.4 "MFMA 布局转置"到底是什么

全篇反复出现的 Pᵀ / dSᵀ 纯寄存器重分布（§3.4），其硬件底座就是 MFMA 的 TransposedCDistribution 变体（让 MFMA 把输出 C 直接落成转置布局的分布，见术语速查）。dispatcher 里每个 f16 形状都成对出现：普通版 + …TransposedCDistribution 版（warp_gemm_dispatcher.hpp:41 / 43 / 47 / 57，对应 32×32×8 / 32×32×16 / 16×16×32 / 16×16×16 四对）。两者算的乘加完全一样，只是把 C 结果换一种 lane→寄存器 的落点，使它直接对齐下一颗 GEMM 期望的操作数布局。

反向 policy 正是给 gemm_1（产 dV）和 gemm_3（产 dK）打开了这个开关（模板第 7 参 TransposeC=true，policy line 80 / 147），而 gemm_0/2/4 用普通版（false，line 46 / 113 / 180）。这两颗恰好就是 A 操作数需要转置喂入的 GEMM（Pᵀ、dSᵀ）。于是上一颗 GEMM 算出的中间结果不必写出去物理翻转，由 PTFromGemm0CToGemm1A / SGradTFromGemm2CToGemm3A（pipeline 643 / 704）在寄存器里做最后一步 lane 重排即可喂给下一颗——全程零 LDS 往返。

换个读法（快）
Pᵀ / dSᵀ · 寄存器重分布
数据已在 64 lane 的寄存器里，靠 MFMA 的转置 C 分布 + lane 重排"换种读法"，零 LDS 往返。对应 gemm_1/gemm_3。
真搬一遍（慢）
Kᵀ / Qᵀ / dOᵀ · LDS shuffle
必须把数据写进 LDS、按转置坐标再读回（§3.4）。因为转置要跨 lane 交换，而寄存器是 lane 私有的，只能借共享内存中转。
题外一笔
SwizzleA 是另一回事
dispatcher 还有 SwizzleA 开关（policy 里 WarpTile==16 ? false : true 那项，line 47/114）——它是 A 操作数排布的另一种优化，与这里的 C 转置分布无关，别混。

5.4½ 追问：k_reg 也排好了分布，凭啥 Kᵀ 不能像 Pᵀ 那样免费转置？

这是读者最常卡住的一问：k_reg 读进寄存器后明明也按 lane 排好了，跟 MFMA 算出的 P 同样住在"64 lane 的寄存器"里——为什么 P 能便宜地变成 Pᵀ，Kᵀ 却非得过 LDS？答案分三层。

① "在寄存器里排好了" ≠ "排成便于便宜转置的样子"

一个 tile 在寄存器里，是 64 lane 各存一部分，按某个 lane→元素 映射摊开。关键在于：MFMA 的输入(A/B)分布与输出(C)分布是两套不同的 lane 映射——A/B 落 ArchVGPR（普通向量寄存器）、是一套；C 落 AGPR（累加专用寄存器，见术语速查）、group = lane/16, col = lane%16、每 lane 握 16 个值，是另一套（rocm-ref mfma-register-layout.md）。所以"都在寄存器里"绝不等于"布局能随便互换"。

一次转置便不便宜，只取决于「源映射 → 目标映射」差的那个 permute 模式：

便宜档
DPP 可表达
只差一个 DPP（Data Parallel Primitives，= 零成本的行内跨-lane 搬运修饰符，见速查）模式（16-lane 行内移位/旋转、少数固定跨行）→ 挂在 VALU 指令上，0 额外开销。
昂贵档
任意 lane↔lane
要任意 lane 全交换 → 得 ds_permute（~20 周期、走 LDS 硬件单元，见速查）或干脆 LDS 往返。
结论
"免费"只指 DPP 那一档
所谓"便宜的寄存器 permute"特指 DPP 档；任意 2D 转置本就不便宜。
出处 rocm-ref cross-lane-ops.md（CDNA3/4）：DPP modifier「0 extra, VALU, within 16-lane row」；ds_permute/ds_bpermute「~20 cycles, LDS unit, any lane in wave64」（借 LDS 路由硬件但不占 LDS 存储）。

② P→Pᵀ 便宜：因为 P 是 MFMA 算出来的，可让矩阵核心"直接吐成转置版"

gemm_0 打开 TransposedCDistribution（dispatcher 专门变体，见 §5.4），让 MFMA 把累加结果 C 直接写成（接近）gemm_1 想要的转置 A 布局。矩阵核心写累加器时本来就要决定结果落在哪些 lane/寄存器——选"转置落点"还是"普通落点"是同一次写、零额外成本。最费的那步跨 lane 排布搭在你本来就要跑的 GEMM 写出上，白嫖；PTFromGemm0CToGemm1A 只是再补一点 DPP 档的残差对齐。

一句话：P 的"转置"从没被单独转置过——它一被 MFMA 写出就已经是转置好的。

③ k_reg→Kᵀ 不行：因为 K 是"搬进来的"，没有 MFMA 替它写出

k_reg 是从 LDS 读进的 gemm_0 的 B 操作数；要拿它当 gemm_4 的 Kᵀ（B 操作数），就得对已经摆好的数据做一次真正的 2D 转置。可是没有任何 MFMA 在"生产"K（它是输入数据，被 load 摆进来的），没有累加器写出可以搭便车 → 转置只能自己做 → 落到 ds_read_tr（LDS 转置读，见速查）那条路。

出处 rocm-ref lds-bank-conflicts.md：ds_read_tr_*「enable direct transposed reads from LDS into the layout expected by MFMA … used in composable_kernel for conflict-free MFMA data staging」。对应源码 240–251 的 K → LDS → 转置读 → Kᵀ。

图5½ · 左（olive）：P 由 MFMA 生产，选「转置落点」让 C 直接落成 Pᵀ，再补一步 DPP 残差对齐，全程零 LDS。右（clay）：K 是搬进来的输入数据，没有累加器写出可搭便车，要 Kᵀ 只能借 LDS 做转置读（跨 lane）。

厨房比喻：P 像让厨师装盘时就直接摆成转过来的样子——反正都要装盘，免费；K 是已经端上桌的盘子（从内存搬来的），想换方向只能自己重新摆一遍（过 LDS）。
决定性一句：只有当数据正被某个操作"生产出来"、你能选它落点时，转置才可能免费。P 由 MFMA 生产（选转置输出 → 免费）；K 只是从内存搬入，把它"转着搬过 64 lane"本身就是那个必须借 LDS 的跨 lane shuffle。
直接回答原问：k_reg 排的是 gemm_0 的 B-输入布局，P 排的是 gemm_0 的 C-输出布局；输出布局矩阵核心可自由选落点（能选转置版），输入布局是死的搬入结果（要转只能自己跨 lane）。

5.5 存储层级与 VGPR 压力

把前文反复提到的三级存储，对到 CDNA 的真实硬件：

层级硬件相对快慢 / 容量本 pipeline 放什么
全局HBM（显存）最大、最慢（~300–400 周期）Q/K/V/O/dO/LSE/D 读入；dQ/dK/dV 写出
片上共享LDS（CDNA3 每 CU 64 KB；CDNA4 更大，workgroup 内多 wavefront 共享）居中（~20 周期）转置中转站 + tile 暂存（Kᵀ/Qᵀ/dOᵀ/dS 的 shuffle）
寄存器VGPR（每 lane 私有；CDNA3 = 512 ArchVGPR + 512 AGPR/SIMD）最快、最小（0–1 周期）MFMA 操作数（常驻 K/Kᵀ/V）走 ArchVGPR；累加器 dk_acc/dv_acc（即 MFMA 的 C/D）在 CDNA3 走独立的 AGPR 文件
kr_ktr_vr 把 K、Kᵀ、V 三份都钉在 ArchVGPR、外加 dk_acc/dv_acc 在 AGPR 常驻累加——好处是 KV 带宽只付一次（§3.2），代价是寄存器占用显著上升。CDNA3 上 ArchVGPR 与 AGPR 是两块独立寄存器文件（各 512/SIMD），occupancy 取 max(ArchVGPR, AGPR)，所以这里常驻的三份操作数（ArchVGPR）通常才是占用主因。这笔账直接牵动下一节的 occupancy。

5.6 occupancy：常驻寄存器越多，能并发的 wavefront 越少

GPU 靠"同时驻留很多 wavefront、谁卡在访存就切去算别的"来掩盖延迟。occupancy（占用率）严格说是每个 SIMD 实际驻留的 wavefront 数 ÷ 该 SIMD 上限（CDNA3：每 CU 4 个 SIMD、每 SIMD 最多 8 个 wave），常被通俗说成"一个 CU 能同时塞下多少 wavefront"。CK 侧由 kBlockPerCu 控制（codegen F_occupancy，fmha_bwd.py:275 字段 / 341 使用）。

核心权衡：寄存器总量是定额的（CDNA3：每 SIMD 512 ArchVGPR + 512 AGPR）。常驻 K/Kᵀ/V（ArchVGPR）与 dk_acc/dv_acc（AGPR）占得越多 → 每个 wavefront 的寄存器需求越大 → 一个 SIMD 能同时塞下的 wavefront 越少 → occupancy 越低。占用随 VGPR 用量台阶式下降（如 CDNA3 上 128→129 VGPR 就从 4 wave/SIMD 跌到 3，−25%）。
但 occupancy 并非越高越好：MFMA/计算密集型 kernel 常在 1–2 wave/SIMD 就接近峰值（单 wave 内靠软件流水即可掩盖延迟）。所以 bwd 的 tile 尺寸（kM0/kN0/各 WarpTile）与常驻策略要在"省带宽 / 大 tile 复用"与"保 occupancy"之间反复权衡——这正是 kr_ktr_vr 这类变体的核心取舍之一。

5.7 （延伸）LDS bank 冲突

5.4 里走 LDS 的 Kᵀ/Qᵀ/dOᵀ 物理 shuffle 还有一道隐形成本：LDS 被分成多个 bank（CDNA3：32 个 bank、每 bank 4 字节，bank = (字节地址/4) % 32），若同一拍里多个 lane 命中不同地址但同一 bank就会串行化（bank conflict，最坏 32 路、约 2–32× 变慢；若是同一地址则免费广播、不冲突）。所以 policy 为这些转置精心设计 LDS 描述符的布局（各种 Make*LdsBlockDescriptor、padding 与 XOR swizzle），目的就是错开 bank、让转置读写尽量并行——这也是"走 LDS 转置"虽不得已、却仍要费心优化的原因。
