HSTU Attention Backward — M8（perf）：先量后砍，把 MAIN 浪费的 q-tile 扫描收紧

M8 是性能优化首轮，scope（lead 闸门裁决）= MI（测量基建）+ B2（causal 紧致化）+ B3（window/local 紧致化）。核心：MAIN dqdkdv kernel 的 GetTileRangeAlongY 此前保守全扫 (0,seqlen)，B2/B3 按 mask 结构把 q-loop 收紧到真实 attending 行范围。所有引用以 git show a86529dc:<file> 行号为准。

读者：要 review 这套 bwd 性能优化的工程师（profiling 立靶 → 收紧 → 四方验证，按此顺序读）
TL;DR — 一句话看懂 M8

rocprofv3 实测：MAIN dqdkdv 占 bwd wall-time 84–90%，矩阵核闲 ~90%（MfmaUtil 9.9%），非 memory-bound（MemUnitStalled 0.024%）→ 瓶颈是浪费的 q-tile 迭代。M8 先建零设备码改动的测量基建（MI，behind -perf），再据此把 GetTileRangeAlongY 从全扫收紧：B2 causal MAIN 提速 1.25–1.60×，B3 window/local 提速 4.7–9.8×（窄窗最高）。

1  总览：M8 到底改了什么

一句话：先量（MI）、再砍（B2/B3）、用离线穷举 gate 兜底。

立靶
profiling 锁定瓶颈
MAIN 占 wall-time 84–90%、矩阵核闲 ~90%、非 memory-bound → 靶就是浪费的 q-tile 扫描（GetTileRangeAlongY 保守全扫）。
测量
MI 测量基建
新 hstu_attention_bwd_perf.hpp 唯一计时原语 time_op；perf 字段纯 host、不进 MakeKargs → 设备码字节不变。
收紧
B2 causal + B3 window
hstu_block_masking.hpp 4 个 GetTileRangeAlongY 按 mask 结构收 q-loop：causal 1.25–1.60×、window 4.7–9.8×。
兜底
离线穷举校验器
superset 校验在 B3 抓到 2 个 under-tighten silent-wrong，修后 1.97M checks 全绿。
M8 最易错处： GetTileRangeAlongY 返回的 [y_start, y_end) 必须是真实 attending 行集合的 YTile（kM0）对齐的 SUPERSET。每个被访问 tile 内部仍有 per-pixel IsTokenPairInsideMask 逐元素清零，所以「多扫」只损失性能；但只要范围漏掉任何一个真 attending 行，就是 silent-wrong——结果错却不报错、对拍能侥幸躲过。这正是 B3 两个 bug 的形态，也是离线穷举校验器存在的理由。

3  逐文件 review（为什么这样改）

① hstu_attention_bwd_perf.hpp — 唯一计时原语 新增

  • :30 time_op(bool measure, stream, Fn&& fn, cold=3, nrep=10) 是 bwd dispatch 唯一的计时入口，PRE/memset/MAIN/POST 四段都走它 → per-kernel 归因口径统一。
  • :32-37 measure==false 走裸路径：fn() 只调一次、返回 0，host 行为与「没有 MI」的裸 launch byte-identical。这是不给 -perf 时套件 253/253 与设备码零回归的根基。
  • :39-44 measure==true：cold 次 warmup → ck_tile::gpu_timer（hipEvent）包 nrep 次 → 返回 mean per-launch ms。
  • 头注释（:15-24）写明 measure==false 从不碰设备码（kernel 模板 / kargs 不变）→ 生成的 gfx950 设备符号 byte-identical（co_symbols 零回归 gate 的依据）。
hstu_attention_bwd_perf.hpp:30-45 — 唯一计时原语 time_optemplate <typename Fn> inline float time_op(bool measure, hipStream_t stream, Fn&& fn, int cold = 3, int nrep = 10) { if(!measure) { fn(); // 裸 launch：只跑一次，host 行为与无-MI 完全相同 return 0.f; } for(int i = 0; i < cold; ++i) fn(); // warmup ck_tile::gpu_timer timer{}; timer.start(stream); for(int i = 0; i < nrep; ++i) fn(); timer.stop(stream); return timer.duration() / static_cast<float>(nrep); // mean per-launch ms }

② hstu_attention_bwd_params.hpp — host-only perf 字段 改动

  • :111-120（NoGroup struct，:17 起）新增 measure_perf + perf_{pre,memset,main,post}_ms。关键铁律：注释（:111-116）明示这些字段 HOST-ONLY；NOT passed to MakeKargs——它们只在 host 侧 dispatch 里读，永不进 kernel kargs，所以设备符号 byte-identical。
  • :117 measure_perf=false 默认关；:120 perf_main_ms 注明是瓶颈、B2/B3 的优化目标。
  • :210-214（Group struct，:131 起）镜像同一组字段——batched / group 两路径同口径。
为什么字段加在 params 而非新结构？ 延续 M0 立的军令状——params 是 host↔device 契约。把 perf 做成 host-only 尾段字段，既复用既有传参通道（dispatch 直接读 param.measure_perf），又因不进 MakeKargs 而对 device 完全透明。这是「测量基建不碰设备码」能成立的结构前提。

③ batched / group backward dispatch — PRE/memset/MAIN/POST 包 time_op 改动

  • 两个 dispatch 都 :24 #include "hstu_attention_bwd_perf.hpp"。
  • batched：memset :77、MAIN :90、POST :101、PRE :300 各把原 launch 包进 hstu_bwd_perf::time_op(param.measure_perf, stream, [&]{ ... })，结果写回对应 param.perf_*_ms。
  • group dispatch 同形：memset :97、MAIN :110、POST :120、PRE :258。
  • measure_perf=false 时 time_op 退化为单次裸调用 → dispatch 行为与改动前等价（这是 253/253 与 co_symbols 零回归的运行时保证）。
hstu_attention_batched_backward_dispatch.hpp:90-100 — MAIN launch 包 time_opparam.perf_main_ms = hstu_bwd_perf::time_op(param.measure_perf, stream, [&] { // stream_config{stream,false}; warmup+repeat 由 time_op 负责 // ... 原 MAIN dqdkdv kernel launch（设备码一字未改）... });

④ example_hstu_attention_bwd.cpp — -perf 驱动 + envelope + 5-GEMM FLOPS 改动

  • :135 新增 CLI flag perf（默认 "0"）；:200 measure_perf = arg_parser.get_int("perf")。behind flag：默认关，套件路径不受影响。
  • :624 起的 measure 分支：envelope = 整个 bwd（PRE+memset+MAIN+POST）warmup+repeat（:650 measure_perf=false 走未插桩路径计整体）；per-kernel = 一次 :661 measure_perf=true 的 dispatch 填 perf_*_ms。
  • :632-646 5-GEMM FLOP 模型（GEMM-only，忽略 elementwise）：jagged 按 seqlen 逐 batch 累加、batched 按 phy_seqlen 算，再 ×num_head。
  • :667-674 统一打印 PERF kernel=.. metric=.. value=..（envelope/PRE/memset/MAIN/POST time_ms + envelope/MAIN TFLOPS + total_gemm_flops），供 run_perf_baseline.py 解析进 benchmark.csv。
per-kernel 与独立 profile 互证： -perf 量到的 canonical MAIN 0.263ms、envelope 87% 与独立 rocprofv3 profile（MAIN 266us、87.6%）吻合；连 SiLU 26% 异常（silu/softmax=1.27×）也复现（出处 M8-done.md MI 节）。

⑤ hstu_block_masking.hpp — GetTileRangeAlongY 收紧（主战场，+178 行）改动

4 个 mask 结构各有一个 GetTileRangeAlongY：cross/self × WithLocal/NoLocal。它返回 KV-block [i_x, i_x+XTile) 所对应的 Q-row 范围 [y_start, y_end)（即 GetTileRangeAlongX 的转置），决定 MAIN 的 q-loop 扫多少 tile。M8 前一律返回 (0, seqlen) 全扫。

B2 — NoLocal causal（self :970 / cross :797）

  • 非 causal（!IsMasking，含 P1-1 num_target）= 全注意力，原样返回 (0,seqlen)——已是精确，不动。
  • causal：列 c 被行 r≥c 注意，故 KV-tile 最小列 i_x 最早被行 i_x 命中 → y_start = align_down(i_x)（self 无 q/k 偏移）。
  • contextual 行 [0,ctx) 注意所有 uih 列：tile 触到 uih 区（i_x < max_uih_len）时由行 0 命中 → y_start=0。
  • y_end = seqlen（target 行已在 [i_x, seqlen) 内，安全上界）。实测 MAIN 1.25–1.60×。
hstu_block_masking.hpp:972-997 — NoLocal self（B2 最干净示例）if constexpr(!IsMasking) { // 非 causal：每 Q 行注意每 K 列 -> 范围已精确 return ck_tile::make_tuple(0, seqlen); } else { index_t y_start; if(contextual_seqlen > 0 && i_x < max_uih_len) y_start = 0; // contextual 行注意全部 uih 列 else y_start = i_x - i_x % YTile; // align_down 到 Q tile（self 无偏移） return ck_tile::make_tuple(y_start, seqlen); }

B3 — WithLocal window/local（self :580 / cross :278）

  • 窗口双边带：causal 行∈[col, col+W]；非 causal [col−W, col+W]（W=max_attn_len）。cross 还要叠 diff_q_kv_len 偏移。
  • contextual：y_start=0 且 floor y_end ≥ contextual_seqlen；target/min_full 行：y_end=seqlen。
  • 实测 MAIN 4.7–9.8×，窄窗最高（window16 ~9.8×）。
hstu_block_masking.hpp:278-303 — WithLocal cross（B3，含两处 bug 修复）const index_t W = max_attn_len; const bool ctx_rows = (contextual_seqlen > 0 && i_x < max_k_uih_len); index_t y_start; if(ctx_rows) { y_start = 0; } else { // causal 下沿=对角线(r=col-diff)；非causal 下沿=col-W-diff index_t lo = kUseCausal ? ★ 离线校验器在 B3 抓到 2 个真 under-tighten silent-wrong（未上 GPU 就拦下）：
① 非 causal + min_full：min_full 行（row≥max_id−mf）注意所有列，在非 causal 下落在窗口带下沿之下（物理起点 max_uih_len−mf），最初只在 y_end 处理 → 漏。修：非 causal WithLocal 把 y_start 下沉到 max_uih_len−mf（上方代码 bug#1；causal 不受影响，min_full 仍需 row≥col）。
② cross causal 大 diff + contextual：diff 大时窗口带映射出界（y_end 被 clamp 到 0），但 contextual 行 [0,ctx) 仍 attend → 漏。修：contextual 分支 floor y_end ≥ contextual_seqlen。
→ 修后 1,973,278 checks ALL GREEN。(出处：M8-done.md)

⑥ test/validate_tile_range_y.cpp — 离线穷举 superset gate gate (测试工件，本 commit 外)

  • 为什么离线 gate 比对拍硬：对拍只覆盖跑到的 shape/随机数据，under-tighten 可能侥幸躲过；校验器对每个 KV-tile 穷举枚举真实 attending 行集合，断言 GetTileRangeAlongY 返回的范围是其 YTile 对齐 superset——一旦漏行立即 FAIL，比 GPU 跑早、比对拍硬。
  • B2+B3 扩到 cross + WithLocal + 2 种 tile 形状后 1,973,278 checks ALL GREEN；reverse-proof：故意破坏一处收紧 → 校验器 FAIL，证明它非 vacuous（不是永远 PASS 的空壳）。
  • 上面两个 bug 正是它抓出来的——这是 M8 的硬价值：把 silent-wrong 挡在 GPU 之外。(出处：M8-done.md / commit message)

4  设计动机小结

  1. 先量后砍，靶要 profiling 立：rocprofv3 量出 MAIN 占 84–90%、矩阵核闲 ~90%、非 memory-bound，才确认「砍浪费的 q-tile 扫描」是对的靶——不靠直觉优化。
  2. 测量基建不碰设备码：time_op（perf.hpp:30）measure=false 退化裸 launch + perf 字段 host-only 不进 MakeKargs（params:111-116）→ 设备符号 byte-identical，MI 自身零回归。
  3. 收紧只改范围、不改正确性：每个 tile 内 per-pixel mask 照常清零，GetTileRangeAlongY 只需返回真实 attending 集合的 YTile 对齐 superset——把「收紧」与「掩码语义」解耦。
  4. 离线穷举 gate > 对拍：superset 校验穷举所有 tile，比对拍更早更硬地挡 under-tighten silent-wrong；B3 两个真 bug 即被它抓出（1.97M checks GREEN + reverse-proof 非 vacuous）。
  5. 诚实归因，不吹模型：实测低于 [derived] 模型就照实记并用 Amdahl 解释（K/V load + atomic 写 + 启动开销不随 q-loop 同比缩）。

5  遗留 / 边界（M8 明确不做）

占用率类经 profiling 证伪 / 低 ROI 暂缓——M8 只做 runtime 真赢的 MI+B2+B3。

暂缓项为什么不做（profiling 依据）归宿
B4 grid widening"grid starvation 根因" 被实测证伪：256× 超额订阅非饥饿，依据作废后续 / 已否
B7 hd256 occupancy / VGPRVGPR 真值 248（rocprofv3 报半值 124）；MAIN 实为 VALU/SFU-bound（VALUBusy 41% ≫ MfmaUtil 18%），提 occupancy 需同砍 VGPR<170+LDS<21KB，要 tile 重设计，低 ROI后续
B1 group TU splitbuild-axis 优化，可日后并行，不影响 runtime后续
B6 trload高风险高工，本期不碰后续
近似 sigmoid（SiLU 26%）根因 = sigmoid 本质需 exp+rcp 两超越运算（softmax 单 exp2），sig 已 CSE，非 bug；近似式有精度/对拍风险后续（精度权衡）
真限制器（INV 定论）： per-block LDS/VGPR 在 2 blocks/CU 处 co-limit（非 grid 数）；MemUnitStalled=0.024%（非 memory-bound）。占用率本期不碰，更高 ROI 的方向是降 VALU/transcendental 工作量。(出处：M8-INV-findings.md)
