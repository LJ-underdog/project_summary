主反向 Pipeline 七阶段详解（kr_ktr_vr）

标准 FMHA 反向的主力 kernel：一个 workgroup 钉住一块 KV、沿 query 扫一遍，靠 5 个 Block GEMM + 2 个 elementwise 一趟算出 dQ / dK / dV。从全局图景到七阶段逐行、再到三级存储搬运与 dQ 写回。

TL;DR

这是标准 FMHA 反向的主 kernel（MAIN），承接 PRE-pass 算好的 D = rowsum(O⊙dO)，在一趟主循环里一次产出 dQ / dK / dV。变体名 kr_ktr_vr = K / Kᵀ / V 三者都常驻寄存器。

并行划分：grid 按 (seqlen_k, nhead, batch) 切，每个 workgroup 独占一个 KV tile —— KV 外循环固定不动、Q 内循环扫所有 query。dk_acc / dv_acc 常驻寄存器逐轮累加，循环末一次写出，因独占而无需 atomic。

一圈 hot loop = STAGE 1–7 = 5 个 Block GEMM（gemm_0..4）+ 2 个 elementwise（STAGE 2 softmax 恢复 P、STAGE 5 算 dS）。中枢分叉点是 P 与 dS。

唯独 dQ 特殊：dQᵢ = Σ(所有 KV 块) 会被多个 workgroup 写同一行，必须 update_tile = atomicAdd（默认，line 755），或开 kIsDeterministic 走 store_tile split-workspace（line 751）再由 convert_dq kernel 按固定顺序归约。

1. 总览：主反向 pipeline 的全局图景

本节给"没什么 GPU kernel 基础"的读者先建立全局图景：这个 kernel 在反向链路里处于什么位置、一个 GPU workgroup 到底负责什么、整段计算被拆成哪 5 个矩阵乘、哪些量在寄存器里常驻累加。看懂这张全局图，再去看后面逐阶段的细节才不会迷路。

1.1 一句话定位：它是反向的"主力 kernel"

标准 FMHA（Flash-Multi-Head-Attention）的反向被拆成三个 GPU kernel 接力跑：PRE → MAIN → POST。

PRE (预处理) : 算出 Dᵢ = ∑ₐ dOᵢₐ Oᵢₐ —— 每行一个标量，喂给主循环 MAIN (主力) : 一次产出 dQ / dK / dV <<< 本文讲的就是它 POST (可选收尾): kIsDeterministic 时把 split-workspace 的 dQ 归约成最终 dQ

本文讲的就是 MAIN，对应源码结构体 BlockFmhaBwdDQDKDVPipelineKRKTRVR（文件 779 行，包装它的主 kernel 是 FmhaBwdDQDKDVKernel）。它承接 PRE 算好的 D，在一趟主循环里把 dQ / dK / dV 三个梯度全部算出来。

变体名 kr_ktr_vr 怎么读（name = "kr_ktr_vr"，line 78）：拆成三段 —— kr = K 驻register（K 常驻寄存器）、ktr = Kᵀ 驻register（K 的转置也常驻寄存器）、vr = V 驻register。一句话：把本 workgroup 负责的那块 K、Kᵀ、V 一次性搬进寄存器待命，整个 Q 循环反复复用，不再回显存取。这就是这个变体名字的全部含义。

1.2 并行划分：为什么"KV 在外、Q 在内"

GPU 把整个任务切成很多个 workgroup（一个 workgroup ≈ 一队协同工作的线程，独占一块片上资源）。本 kernel 的切法是：grid 按 (seqlen_k 块, nhead, batch) 三个维度切分 —— 也就是说，每个 workgroup 认领一个 KV tile（沿 key 序列方向 seqlen_k 取一块，块大小 kN0）。

认领之后，这个 workgroup 内部是一个双层循环：

外循环：KV 固定不动
我负责的这块 K/V 在整个生命周期里钉死不变，搬进寄存器后就一直在那儿。
内循环：沿 Q 扫一遍
沿 query 序列 seqlen_q 一块块（每块 kM0）地扫过所有 Q，每轮处理一个 Q tile。
num_total_loop = ceil((seqlen_q_end − seqlen_q_start)/kM0)（mask 早退裁剪后的 Q 区间，见 §1.4；line 163），热循环 while(i_total_loops < num_total_loop)（line 494）。
累加器常驻
扫 Q 的过程中，dk_acc / dv_acc 一直留在寄存器里把每个 Q tile 的贡献累加上去。
为什么是 KV 外、Q 内？（生活化类比）把它想成"给一批快递按收件人归集"。dK/dV 的本质是"对某一个 key，累加所有 query 对它的贡献"（数学上 dKⱼ = ∑ᵢ dSᵢⱼ Qᵢ，对 query 下标 i 求和）。既然结果是"按 key 归集、对所有 query 求和"，那就把这个 key（KV）固定在手边，一个个 query 拿过来累加最自然 —— 累加器 dk_acc/dv_acc 可以全程待在寄存器里，扫完所有 Q 再一次性写出。反过来若把 Q 固定在外、KV 在内，每换一个 KV 都要把半成品的 dK/dV 写回显存再读回来，得不偿失。
图 1 — 并行划分：一个 workgroup 钉住一列 KV，沿 seqlen_q 逐块扫所有 Q；dk_acc/dv_acc 在寄存器里累加。

1.3 全程只有 5 个矩阵乘（Block GEMM 总表）

别被七个 STAGE 吓到 —— 整个主循环的"重活"其实只有 5 次矩阵乘法（Block GEMM）。它们在循环开始前就被声明好（line 141-145），每个由一个编译期 Policy 决定如何拆 tile。先记住这张表，后面每个 STAGE 不过是"做其中一两个 GEMM + 一些逐元素处理"。

GEMM 变量Policy 取法数学式所在 STAGE产出
gemm_0GetQKBlockGemmS = Q @ KᵀSTAGE 1分数矩阵 S
gemm_1GetPTOGradTBlockGemmdV += Pᵀ @ dOSTAGE 3累加 dv_acc
gemm_2GetOGradVBlockGemmdP = dO @ VᵀSTAGE 4dP
gemm_3GetSGradTQTBlockGemmdK += dSᵀ @ QSTAGE 6累加 dk_acc
gemm_4GetSGradKTBlockGemmdQ += dS @ KSTAGE 7dq_acc → 写回
一句话串起来：先 gemm_0 还原分数 S，softmax 恢复出 P；然后 gemm_1 用 P 攒 dV、gemm_2 用 dO 算出 dP，gemm_3 攒 dK、gemm_4 算 dQ。5 个 GEMM 对应了反向 5 条梯度公式，剩下的都是 scale / mask / softmax / 逐元素这些"配菜"。术语：P = softmax 概率矩阵，S = 未归一化分数，dX = 对 X 的梯度，上标 ᵀ = 转置。Policy 名里的 T（GetPTOGradT/SGradTQT/SGradKT）指 MFMA（CDNA3/4 矩阵核心指令）操作数布局转置，与上方"数学式"列是同一运算的两种记法，详见 §2 图4 下注。

1.4 常驻累加器 & 早退优化

常驻累加器（line 148-149）：dv_acc（gemm_1 的输出）和 dk_acc（gemm_3 的输出）在循环开始前就声明在寄存器里，跨整个 Q 内循环存活，把每个 Q tile 算出的贡献一路累加上去，循环结束后一次性写出。

为什么 dK/dV 不用 atomic？
本 workgroup 独占这一块 KV，没有别的 workgroup 会往同一块 dK/dV 写 —— 所以寄存器里安静累加、最后落盘即可，无需原子操作。
而 dQ 为什么特殊？
同一行 dQ 会被多个 KV 块（多个 workgroup）共同贡献，存在写冲突 —— 所以 dQ 必须靠 atomicAdd 或独立 split-workspace（详见后续 STAGE 7 部分）。
早退优化（line 165-173）
若该 KV 块被 mask 完全挡住（没有任何 Q 与它交互，num_total_loop ≤ 0），就把 dk_acc/dv_acc 清零直接 return，跳过整段循环。

1.5 数据流分层小抄（HBM / LDS / Register）

GPU 的存储是三层金字塔，越往下越快越小。看懂"什么东西放在哪一层、谁常驻谁流式"，是理解这个 pipeline 性能取舍的钥匙：

HBM（显存，大而慢） : 读入 Q/K/V/O/dO/LSE/D ; 写出 dQ/dK/dV LDS（片上共享内存） : 转置中转站（Kᵀ/Qᵀ/dOᵀ 的 shuffle）+ tile 暂存（dS 也借 LDS 重切） Register（寄存器最快） : GEMM 的输入/输出 tile ; dk_acc/dv_acc/dq_acc 累加器 典型搬运链 : HBM → Reg → LDS(shuffle 转置) → Reg → GEMM

关键区分是常驻 vs 流式：

  • 常驻（一次载入、整循环复用）：K、Kᵀ、V —— 即 kr_ktr_vr 三件套，循环开始前搬进寄存器就钉住不动。
  • 流式（每轮循环重新载入）：Q、dO、LSE、D —— 每处理一个 Q tile 就从 HBM 拉一份新的进来。
图 2 — 数据流三层：KV（clay）一次载入常驻寄存器；Q/dO（olive）每轮流式；5 个 GEMM 与累加器都在寄存器层。
承上启下：到这里你已经有了全局图景 —— 一个 workgroup 钉住一块 KV、沿 Q 扫一遍、靠 5 个 GEMM 攒出三个梯度、KV 常驻 Q 流式。接下来的部分会逐个 STAGE 拆开看这趟主循环里到底发生了什么（gemm_0 怎么算 S、softmax 怎么单趟恢复 P、dQ 两条写回路怎么选），以及显存搬运/转置的更深细节。

2. 七阶段逐阶段拆解

本节是全篇核心。hot loop（while(i_total_loops < num_total_loop)，line 494）每转一圈处理一个 Q tile（kM0 行），与本 workgroup 固定不动的 KV tile（kN0 行）做一整套反向计算，把贡献累加进常驻寄存器 dv_acc / dk_acc，并把 dQ 写回显存。一圈之内顺序执行 STAGE 1–7。

承上：循环顶部的搬运（line 496–513）。进入七阶段前，先把本轮 Q tile 与对应的 LSE 从 HBM 流式载入：load_tile(q_dram_window) → 写 LDS → shuffle_tile 转置出 Qᵀ 也一并存好 → 再 load_tile 回寄存器得 q_reg_tensor 与 lse。两次 block_sync_lds() 夹着 LDS 读写以保证可见性。Qᵀ 此刻就备好，STAGE 6 直接取用。

依赖链一眼看懂（不是孤立 7 步）

真正的脉络是一条依赖链：S(1) → P(2)，然后 P 同时喂给 dV(3) 和 dS(5)；dP(4) 也喂给 dS(5)；dS(5) 再同时喂给 dK(6) 和 dQ(7)。中枢是 P（STAGE 2）与 dS（STAGE 5）——前者是 softmax 概率，后者是 softmax 的反向梯度（Jacobian 落地）。看懂这两个分叉点，整套 pipeline 的排布顺序就顺理成章。

图3 · 七阶段流水与依赖链：实线灰=代码顺序流；彩色实/虚线=数据依赖。中枢分叉点是 P（STAGE 2）与 dS（STAGE 5）。

为什么单趟
LSE 已存
前向把每行的 LSE = max + log Σexp 存进 HBM。反向直接 P = exp(s − LSE)，免去重新求 max 与归一化，省一遍 reduce。
为什么 exp2
硬件指令
CDNA(gfx942) 的硬件指数指令原生以 2 为底（v_exp_f32 即算 2ˣ，属超越函数 VALU）。用 log2e_v 把底从 e 换到 2：exp(x)=exp2(x·log2e)，scale 与 log2e 提前折进指数，少一次乘法。
为什么 -inf
mask 即归零
越界/因果遮挡位置置 -∞，exp2(-∞)=0，自然让被遮位置概率为 0，无需额外分支。

2.5 STAGE 5 — dS = P ⊙ (dP − D)（softmax Jacobian 落地）

② 计算Elementwise（无 GEMM）：逐元素 ds = p · (dp − d)；可选算 dBias
③ 输出ds：分数梯度 dS，[kM0,kN0]（AccDataType）
④ 行号line 657–696（核心 659–669；可选 dBias 671–696）

这就是 softmax 反向的数学心脏。前向 P = softmax(S) 的 Jacobian 给出 dS = P ⊙ (dP − rowsum(P⊙dP))，而 rowsum(P⊙dP) 恰等于 PRE 存的 D（因 O = P·V ⇒ 该 rowsum = Σ O⊙dO）。所以这一步把 dV/dK/dQ 全部依赖的 dS 一次性算出——它是第二个分叉中枢。

dS 太宽，沿 kK4 切成 k4_loops 块；用 ds_reg_tensor_next 提前 load_tile 下一块，与本块 gemm_4 重叠，隐藏 LDS 读延迟。
写回路 A
deterministic
kIsDeterministic==true：store_tile 到独立 split-workspace，每块各写各的，事后由 convert_dq kernel 归约求和——结果可复现。
写回路 B
atomicAdd
否则 update_tile = 原子累加直接落到 dQ。快但浮点加法顺序不定 ⇒ 非确定。
为什么唯独 dQ 要特殊处理：dQ_i = Σ over 所有 KV 块。同一行 dQ 会被多个 workgroup（各管不同 KV 块）写到，必须 atomic 或 split-workspace 防写冲突；而 dK/dV 每块被单一 workgroup 独占，故只在循环末普通写出。

五颗 GEMM 的张量形状 / 谁乘谁

图4 · 五颗 GEMM 的 [A]·[B]=[C] 形状对位：clay=K/V/dV/dK/dQ 相关，olive=Q/dO 相关，灰=中间张量 S/P/dP/dS。+= 标的是常驻累加器。

关于转置标记（ᵀ）：源码 Policy 名（PTOGradT/SGradTQT/SGradKT）与变量（pt_reg/dst_reg/kt_reg）里的 ᵀ 是为 MFMA 硬件指令（矩阵核心，限 CDNA3/CDNA4 = gfx942/gfx950）准备的布局转置。上图按数学结果给出形状（如 dV = Pᵀ·dO、dQ = dS·K），让维度直观对上；实际寄存器里相应操作数以转置布局驻留。其中 Kᵀ / Qᵀ / dOᵀ 经 LDS shuffle 转置，而 Pᵀ / dSᵀ 是纯寄存器重分布（不落 LDS）——两类机制的区分详见 §3.3。

3. 数据流向与显存层级

前两部分讲了 "逻辑流程"（KV 外循环、Q 内循环、七个 STAGE 各算什么）。本部分把这套逻辑落到 "硬件搬运"：数据真正怎么在 HBM → LDS → 寄存器 三级存储之间来回搬、为什么源码里有那么多看似"绕来绕去"的转置、以及 dQ 写回为什么要特殊对待。理解了这一层，就懂了 kr_ktr_vr 这个变体名字到底在省什么。

3.1 三级存储模型：先认识舞台

GPU（本篇口径：AMD CDNA3 / gfx942 / MI300）算 GEMM 之前，数据必须从慢的地方搬到快的地方。三级存储的角色一句话说清（下列容量/延迟为 CDNA3 数量级）：

Level 1 · 最大最慢
HBM（显存）
容量大（如 MI300X 192 GB）但延迟最高（~300–400 周期）、带宽是瓶颈。Q/K/V/O/dO/LSE/D 从这里读入；dQ/dK/dV 最终写回这里。能少搬一次就少搬一次。
Level 2 · 片上共享
LDS（共享内存）
CDNA3 每 CU 64 KB、约 20 周期，一个 workgroup 内所有线程共享。本 pipeline 里它有两个身份：tile 的暂存区，以及最关键的——"转置中转站"。
Level 3 · 最快最小
Register（寄存器）
最快（0–1 周期）、但线程私有、数量极有限。GEMM 的输入/输出 tile 都在这里；累加器 dk_acc / dv_acc / dq_acc 也常驻寄存器。

核心矛盾：寄存器最快但装不下整块矩阵，HBM 装得下但慢。LDS 夹在中间，既当缓冲、又因为它"对整个 workgroup 可见"而成为做跨线程数据重排（转置）的唯一可行场所——这正是下面 3.2、3.3 反复出现 LDS 的根本原因。

3.2 hot loop 之前：KV 的"一次性装载 + 预转置"

名字 kr_ktr_vr = K in register + Kᵀ in register（ktr）+ V in register（源码 name = "kr_ktr_vr"，line 78）。也就是说，本 workgroup 负责的那一个 KV 块，会在进入 hot loop 之前就被搬进寄存器并备好转置版本，然后整个 Q 内循环里反复复用，全程只搬这一次。

三个量的搬运链（声明 line 151–258，实际搬运动作 line 240–258）：

量 搬运链 关键源码行
K HBM → LDS → Reg（直载，不转置） load 240 → store_tile LDS 243 → load_tile Reg 248
V HBM → LDS → Reg（直载，不转置） load 241 → store_tile LDS 253 → load_tile Reg 257
Kᵀ Reg →(shuffle)→ LDS → Reg（预转置） shuffle_tile 244 → store_tile LDS 245 → load_tile Reg 251

注意 K 被搬了两遍：一遍直载得 k_reg_tensor（给 STAGE 1 的 S = Q@Kᵀ 当操作数），一遍经 shuffle_tile 转置得 kt_reg_tensor（给 STAGE 7 的 dQ += dS@Kᵀ）。这就是 kr 和 ktr 同时出现的原因——同一块 K，两种布局都预先备在寄存器里，免得在 hot loop 里反复转。

// line 240-258 —— hot loop 之前，只执行一次 auto k_block_tile = load_tile(k_dram_window); // K: HBM -> Reg auto v_block_tile = load_tile(v_dram_window); // V: HBM -> Reg store_tile(k_lds_write_window, k_block_tile); // K -> LDS shuffle_tile(shuffled_k_block_tile, k_block_tile); // K 在寄存器内做 lane shuffle store_tile(shuffled_k_lds_write_window, ...); // 写进 LDS（转置中转） block_sync_lds(); k_reg_tensor = load_tile(k_lds_read_window); // LDS -> Reg 得 k_reg (kr) block_sync_lds(); auto kt_reg_tensor = load_tile(kt_lds_read_window); // 用"转置后的描述符"读回 得 kt_reg (ktr) store_tile(v_lds_write_window, v_block_tile); // V -> LDS block_sync_lds(); auto v_reg_tensor = load_tile(v_lds_read_window); // LDS -> Reg 得 v_reg (vr)

"转置"的玄机在于：写进 LDS 用一种布局，读出来时用另一套坐标描述符（MakeKTLdsReadBlockDescriptor / MakeKTRegBlockDescriptor），于是同一片 LDS 数据被"按转置后的方向"重新读出。LDS 的"全 workgroup 可见"在这里是必需的——转置要跨线程交换数据，寄存器私有做不到。

3.3 为什么需要那么多转置？

根因是 GEMM 指令对操作数的布局有固定要求（哪个维度连续、谁当 A 谁当 B）。一个 tile 在上一步算出来的布局，往往不是下一个 GEMM 想要的布局，于是必须转置。本 pipeline 里需要转置的量有 Kᵀ / Qᵀ / dOᵀ / Pᵀ / dSᵀ。它们走两种不同机制：

机制 A · 经 LDS 中转
Kᵀ、Qᵀ、dOᵀ
典型链 HBM→Reg→shuffle→LDS→Reg。借 LDS 的全局可见性跨线程重排。
Qᵀ：line 503 shuffle→504 写 LDS→699 读回；dOᵀ：632→633→639。
机制 B · 纯寄存器重分布
Pᵀ、dSᵀ
不落 LDS，由 Policy 助手把上一个 GEMM 的 C 输出直接重分布成下一个 GEMM 的 A 输入。
Pᵀ：PTFromGemm0CToGemm1A（643-645）；dSᵀ：SGradTFromGemm2CToGemm3A（704-706）。

两个具体例子，看转置为什么躲不掉：

  • STAGE 3 需要 Pᵀ 和 dOᵀ（算 dV += Pᵀ@dOᵀ，gemm_1，line 646）：P 是 STAGE 2 softmax 出来的 kM0×kN0，dO 是按行载入的；但 gemm_1 要的是它们的转置形态。Pᵀ 走机制 B（从 gemm_0 的 C 直接重分布，643-645），dOᵀ 走机制 A（经 LDS，639）。
  • STAGE 6 需要 Qᵀ（算 dK += dSᵀ@Qᵀ，gemm_3，line 708）：Q 在 STAGE 1 是按 q_reg 布局用的，到这里要换成转置布局 qt_reg（line 699 从 LDS 读回，机制 A）；dSᵀ 走机制 B（704-706）。

LDS 是被复用的转置中转站。源码里 qt_lds_ptr 直接复用 smem_ptr 基址（line 291），Kᵀ 用 smem_ptr + GetSmemSizeK（line 220-221）——也就是说同一片 LDS 在不同阶段被 Kᵀ、Qᵀ、dOᵀ、dS 等量轮流借用。LDS 容量小，只能这样"分时复用"，这也是各种 GetSmemSize* 偏移量计算（line 267-270、333-335、353-358…）存在的原因。

图 5　两条搬运链（直载 vs 转置）与"常驻 KV / 流式 Q"的带宽对比。转置之所以非经 LDS 不可，是因为它需要跨线程交换数据，而寄存器是线程私有的。

3.4 常驻 vs 流式：带宽账本

把 3.2、3.3 的搬运换算成"搬了几次"，就看清 kr_ktr_vr 在优化什么了。设 Q 内循环跑 num_total_loop = ceil((seqlen_q_end − seqlen_q_start)/kM0) 轮（line 163）：

数据 载入次数（每 workgroup） 位置
K / V / Kᵀ 1 次（hot loop 之前，240-258） 常驻寄存器，全程复用
Q / LSE num_total_loop 次（496-500，每轮 move 窗口） 流式：用完即弃
dO / D num_total_loop 次（625-629） 流式：用完即弃

为什么这样分？呼应第 1 部分的并行划分：本 workgroup 独占一个 KV 块、要扫所有 Q。KV 在整个循环里不变 → 一次载入、常驻寄存器最划算；Q/dO 每轮都换 → 只能流式。kr_ktr_vr 的全部价值就在"把 K、Kᵀ、V 钉死在寄存器里"，让占比最大的 KV 带宽只付一次。代价是寄存器压力变大（K 还存了转置副本），这是典型的带宽换寄存器权衡。

3.5 dQ 写回的两条路（重点）

dK / dV 用常驻累加器 dk_acc / dv_acc 攒完整个 Q 循环，循环结束后一次性返回（line 775）——因为每个 KV 块被唯一一个 workgroup 独占，没人和它抢，无需 atomic。但 dQ 不一样：

dQi = Σ(所有 KV 块 j) dSij @ Kᵀj　　← 同一行 dQi 被多个 workgroup（每个负责不同的 KV 块 j）同时贡献

也就是说，不同 workgroup 会写到同一行 dQ，必然冲突。源码用 kIsDeterministic 在两条路里二选一（line 749-756）：

// line 749-756 —— STAGE 7 末尾，dQ 写回 if constexpr(kIsDeterministic) { store_tile(dq_dram_window, dq_acc); // 路 B：各写各的 split-workspace 分片 } else { update_tile(dq_dram_window, dq_acc); // 路 A：atomicAdd 直接累加到 dQ }
路 A · 默认
update_tile = atomicAdd（755）
每个 workgroup 用原子加直接把自己的 dq_acc 累进 HBM 里的 dQ。简单、省内存，但有原子争用开销，且浮点求和顺序随调度而变 → 结果非确定（不可逐位复现）。
路 B · kIsDeterministic
store_tile → split-workspace（751）
每个 workgroup 把结果 store 到各自独立的分片（互不重叠，无需 atomic），事后由单独的 convert_dq kernel 按固定顺序归约求和 → 结果可复现。代价：额外 workspace 显存 + 一趟归约 kernel。

权衡一句话：路 A 拿"非确定 + 原子争用"换"省显存、少一趟 kernel"；路 B 拿"额外显存 + 归约开销"换"逐位可复现"。（atomicAdd(FP32) 在 CDNA3 是硬件原生指令 buffer_atomic_add_f32、无需 CAS 循环；但全局原子要经 Data Fabric 串行化，且浮点加法不满足结合律，求和顺序随调度而变 ⇒ 非逐位确定。）需要 bit-wise 可复现（如调试、严格回归对齐）时开 kIsDeterministic，否则默认走 atomicAdd。dK/dV 因独占而完全没有这个烦恼——这是 dQ 在整个反向里唯一需要特判写回的量。

图 6　dQ 写回两条路。左：所有 workgroup 用 atomicAdd 抢写同一行 dQ（争用、非确定）；右：各写各的独立分片，再由 convert_dq kernel 按固定顺序归约（确定、但需额外显存与一趟 kernel）。
