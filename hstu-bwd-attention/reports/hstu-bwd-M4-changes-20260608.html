HSTU Attention Backward — M4（group 模式）改了哪些代码、为什么、怎么连

这份文档忠实记录 M4 里程碑在仓库里真实发生的代码改动：group（多组、每组独立超参）怎么复用 M3 的 jagged 内存索引、per-group 超参怎么用 i_group 从设备指针读、以及 M4 最硬的难点——per-group window 无法编译期固定 → 运行时在两条 pipeline 间二选一。所有片段以当前源码为准（bwd 文件未跟踪，无 git 基线，按 M2/M3 文档同法以代码区段呈现）。

读者：要 review 这套 bwd group 实现的工程师（零基础友好，关键术语都配一句白话）
代码目录：ck_hstu/example/ck_tile/18_hstu_attention/  ·  主目标 gfx950 (MI350/CDNA4)  ·  落点 2026-06-08  ·  接续 M3 jagged 文档
TL;DR — 一句话看懂 M4

M4 的核心认知：group = jagged 的超集。内存布局完全一样（dim0=1 token-major packed [1,ΣL,H,D] + cu_seqlens），M3 的 offset 索引直接复用。差别只在「超参的粒度」：scale_p 和 mask 的 4 个参数（window / contextual / min_full / max_seqlen）从单标量变成 per-group 设备指针，kernel 用 i_group = i_batch / num_batch_per_group 取；alpha 仍全局、num_target 仍 per-batch。

最硬的难点：同一次 launch 里不同 group 的 window 可以是 0 或 >0，无法把 kUseLocal 固定成编译期常量。解法是镜像 fwd kernel —— 同时实例化 with-local + without-local 两条 pipeline，kernel 内用 if(window>0) 运行时选一条跑。

1  总览：M4 到底改了什么

M4 = 在 M3（jagged 变长）已通过的基础上，让反向支持 group（每组带独立超参）。核心理念一句话：布局复用 jagged，超参升级为 per-group 设备指针，window 维度改运行时双 pipeline 选择。

白话：M4 的四件事

  • ① 填充 GroupBwdParams（hstu_attention_bwd_params.hpp）：复用 jagged 全部输入/输出/workspace，再加 5 个 group_*_ptr 设备指针 + num_group/num_batch + 全局 alpha。
  • ② 新增 group kernel（hstu_attention_bwd_kernel.hpp 的 HstuAttentionBwdDQDKDVGroupKernel）：jagged offset 复用 + i_group 取 per-group 超参 + 运行时 if(window>0) 双 pipeline 选择 + 共享 write_dkdv。no_group kernel 一行没改。
  • ③ 新增 group dispatch / entry（...group_backward_dispatch.hpp + ...group_backward_bf16.cpp）：组两条 Problem/Pipeline、grid、POST；entry 用 BOOL_SWITCH_2 直接实例化（无 instance 文件）。
  • ④ harness -g + 测试（example_hstu_attention_bwd.cpp + test/run_bwd_tests.py）：6 个 -g* 参数、per-group 数组 supplement、喂 reference_group_…；reject-group-g2 → 8 个 pass。
为什么 group 能复用 jagged？ 两者的内存布局完全相同 —— 都是把所有 batch 的 token 沿 dim1 紧密拼成 dim0=1 的 packed 张量。group 只是在「逻辑上」把相邻的 num_batch_per_group 个 batch 归为一组、共享一套超参。所以 kernel 定位 batch 的代码（base offset、per-batch seqlen、early-exit）原样照搬 M3，只多一步「从 i_batch 算 i_group 再去读 per-group 数组」。
诚实声明（与 M3 一致）：M4 本次同样无 instance 噪音。 group entry 用 BOOL_SWITCH_2 在 .cpp 里直接实例化 run_group_backward_dispatch，不走 extern-template 的 instance 文件机制 —— 没有任何新 instance 文件，也没重跑 generate_instances.py（实测它 mtime 仍是 06-04，M4 改的文件是 06-08）。git status 里仍挂的 ~203 个 instance 修改是 M2 期遗留，与 M4 无关。详见 §2。

4  【图2】运行时双 pipeline 选择（M4 核心难点）

这是 M4 最硬的一处。前面里程碑里 window>0（local）是编译期用 BOOL_SWITCH 定的；但 group 模式下同一次 launch 里不同 group 的 window 可以一个是 0、一个是 16，没法用一个编译期常量描述。

图2：dispatch 编译期实例化 with-local / without-local 两条 pipeline（同 causal）；kernel 内按 per-group window_size 运行时二选一，两分支跑完共用 write_dkdv 写回。

代价与收益： 代价是两条 pipeline 都被编译进二进制（代码体积↑，属 perf 项 M8），但运行时每个 block 只跑其中一条。收益是同一次 launch 能正确处理「有的 group 带 window、有的不带」的真实异构负载 —— 这正是 group 模式存在的意义。

5  per-group scale_p / mask 取数（代码）

kernel 进来先复用 jagged 定位 batch，再算 i_group，从 5 个设备指针读 per-group 超参，最后定 scale_p。注意 num_target 仍按 i_batch 取（不是 i_group）。

hstu_attention_bwd_kernel.hpp（~L643–675） // jagged offsets (token-major packed; same as M3) const long_index_t query_start = q_offsets[i_batch]; const long_index_t key_start = kv_offsets[i_batch]; const index_t seqlen_q = q_offsets[i_batch + 1] - q_offsets[i_batch]; const index_t seqlen_kv = kv_offsets[i_batch + 1] - kv_offsets[i_batch]; // grid.x sized to the largest group seqlen -> early-exit OOB KV tiles if(i_n0 >= seqlen_kv) return; // per-group hyper-params (D6): i_group = i_batch / num_batch_per_group const index_t i_group = __builtin_amdgcn_readfirstlane(i_batch / kargs.num_batch_per_group); const float group_attn_scale = ...group_attn_scale_ptr[i_group]; const index_t group_max_seqlen_q = ...group_max_seqlen_q_ptr[i_group]; const index_t window_size = ...group_window_size_ptr[i_group]; const index_t contextual_seqlen = ...group_contextual_seqlen_ptr[i_group]; const index_t min_full_attn_seqlen = ...group_min_full_attn_seqlen_ptr[i_group]; const float scale_p = (group_attn_scale != 0.f) ? group_attn_scale : 1.0f / static_cast<float>(group_max_seqlen_q); const int num_target = (kargs.num_targets_ptr != nullptr) ? ...num_targets_ptr[i_batch] // per-BATCH，不是 i_group : 0;
取数 1
i_group 用 readfirstlane
i_group 在一个 wave 内对所有 lane 相同，用 __builtin_amdgcn_readfirstlane 提示编译器它是 scalar，省 VGPR、走标量寄存器读。
取数 2
scale_p 的 fallback
group_attn_scale==0 时回退到 1/group_max_seqlen_q。GPU 与 reference 用同一向量 group_max_seqlens_q，保证 fallback 一致。
取数 3
num_target 仍 per-batch
同一 group 内不同 batch 可有不同 num_target，所以它按 i_batch 取；这点 group 与 jagged 一致，没升级到 per-group。

SiLU 路跳过 GPU forward。 SiLU 反向不需要前向的 O（O 只在 softmax 路要），所以 group harness 不跑 GPU fwd，直接造随机 Q/K/V/dO + cu_seqlens 喂 bwd 与 reference。group 恒为 jagged-packed，所以 reference 模板没有 kIsJagged 轴（与 M3 的 BOOL_SWITCH_3 不同，这里是 BOOL_SWITCH_2）。

10  遗留与边界（诚实标注）

  • M5 softmax：group / no_group 现均 throw。需 PRE（D = rowsum(O·dO)）+ 读 LSE + STAGE5 ds = p*(dp − d)。group softmax 的 O 在 harness 现被跳过，M5 要接 group GPU fwd 产 O + LSE。
  • cross-attention：group / jagged 现仅 self（kv offsets == q）；cross 需独立 kv offsets + cross mask 构造（mask 成员 M2 已加），待对应里程碑。
  • 双 pipeline 代码体积（perf M8）：with-local / without-local 两条都实例化进二进制，运行时只跑一条；grid 仍按 max_seqlen 开；GetTileRangeAlongY 仍保守全 Q 扫描（M2 遗留）。这些是 perf，不影响正确性。
  • M6 deterministic / M7 fp16+hdim：group dispatch 已留 throw 门；deterministic 的 dq_acc 多 split + reduce POST、fp16 / hdim96-256 待接。
  • 验证包络（口径说明）：所有 mask 因子（window / contextual / min_full / num_target）的对拍均在 causal=1 下进行；causal=0 在本系列里一直作为 no-mask 路径（M1 闸门定义）。把 mask 因子叠加到 causal=0 之上属当前未验证区间——已在代码 review 中单独留档交 lead 评估，不在本文档展开。
