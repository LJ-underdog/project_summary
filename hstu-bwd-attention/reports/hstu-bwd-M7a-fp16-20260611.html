HSTU Attention Backward — M7a：fp16 怎么靠「复用 bf16 同一套模板码路」做对的

这份文档讲清 M7a 如何把 bwd 从 仅 bf16 扩到 bf16 + fp16——而且不重写一行 kernel。重点：为什么 dispatch/kernel/pipeline 早就模板化于 InOutDataType 使 fp16 只需在边界加 dtype；fp16 容差为何比 bf16 更紧（10bit 尾数 vs 7bit）；怎么用 fp16-ULP 误差量级反证「真在跑 fp16 而非静默落回 bf16」；容差没放水的双向 revert 实验；以及零回归的 byte-level 证据。范围诚实标注：仍 hd64 + hdim_qk==hdim_v，hdim{96,128,256} 与 hdim_qk≠hdim_v 是 M7b/M7c。所有片段引磁盘真实行号（git bf82a1d2）。

TL;DR — 一句话看懂 M7a

bwd 的 dispatch / kernel / pipeline 从 M0 起就模板化在 InOutDataType 上，且内部累加恒为 float（GemmAccDataType）——dtype 只活在「读输入 / 写梯度」的边界。所以加 fp16 不是写新 kernel，而是把同一套模板换个 dtype 实例化：新增两个 fp16 entry（与 bf16 版逐字镜像，仅 bf16_t→fp16_t）、8 个 fp16 instance + ref、harness 按 -prec 运行时选类型、CMake glob 进来。库 kernel / pipeline / dispatch / reference 一行未改。

fp16 尾数 10bit > bf16 7bit，存储更准 → 容差收紧到 rtol5e-3 / atol1e-2（bf16 是 2e-2 / 5e-2）。实测 fp16 误差落在 fp16-ULP（2⁻¹⁴）量级，比 bf16-ULP 约小 8×——这正是「确在跑 fp16」的铁证（若静默落回 bf16，误差会大约 8 倍）。

1  M7a 是什么：纯 dtype 轴，复用而非重写

M7a 只做一件事：把反向支持的 I/O 数据类型从 {bf16} 扩成 {bf16, fp16}。不动 hdim（仍 64）、不动 hdim_qk≠hdim_v（仍相等）、不动任何 kernel 算法。能这么省，是因为整套 bwd 的数值结构早就把 dtype 隔离在边界上。

关键不变式（fp16 与 bf16 完全对称）： HstuAttentionFwdTypeConfig<fp16_t>:: GemmAccDataType = float , CompDataType = float HstuAttentionFwdTypeConfig<bf16_t>:: GemmAccDataType = float , CompDataType = float ⇒ 矩阵乘累加 / softmax exp / LSE / 梯度归约 全在 float 里算，fp16 只活在 load Q/K/V/dO + store dQ/dK/dV 的边界

【图1】为什么 fp16「只在边界分叉」

同一套 dispatch→kernel→pipeline 模板被 bf16_t 与 fp16_t 两次实例化。中间所有计算逻辑（5 个 GEMM、softmax、SiLU、mask、determ split、POST reduce）是同一份源码、同样的 float 内算；唯一不同的是最外层「读什么 dtype、写什么 dtype」。

图1：fp16 与 bf16 共享中间整套模板（dispatch/kernel/pipeline/POST），内算恒为 float。dtype 只在边界两端（读输入、写梯度）出现。M7a = 加一个 fp16 边界实例化，中间不碰。

3  为什么 fp16 容差比 bf16 更紧

两者都是 16bit、都 1 个符号位，区别全在指数位与尾数位的分配：bf16 给指数 8bit（动态范围同 fp32）、尾数只 7bit；fp16 给指数 5bit、尾数 10bit。尾数位决定相对精度——fp16 多 3 个尾数 bit ⇒ 量化误差约小 2³=8×。所以 fp16 的对拍容差应当收紧，而不是沿用 bf16 的。

图3：bf16（8 指数 / 7 尾数）vs fp16（5 指数 / 10 尾数）。fp16 多 3 尾数 bit → 精度约高 8×，故容差收紧；代价是动态范围小（max 65504）。

example_hstu_attention_bwd.cpp:146-153 — fp16 容差是 bf16 的特化收紧template <typename DataType> auto get_bwd_elimit() // 默认（bf16） { return ck_tile::make_tuple(/*rtol*/ 2e-2, /*atol*/ 5e-2); } template <> auto get_bwd_elimit<ck_tile::fp16_t>() // fp16 特化：更紧 { return ck_tile::make_tuple(/*rtol*/ 5e-3, /*atol*/ 1e-2); }
白话： fp16 容差（rtol 5e-3 / atol 1e-2）比 bf16（2e-2 / 5e-2）紧 4×–5×。这不是把阈值「调松来掩误差」，恰恰相反——是因为 fp16 物理上更准，所以用更严的标尺去验它。§5 用实验证明这把标尺没放水。

4  怎么证「真在跑 fp16，而非静默落回 bf16」

复用同一套模板有个隐患：万一 dtype 没真正切换、harness 实际还在跑 bf16，对拍照样会过（因为两侧都 bf16）。M7a 用一个误差量级反证把这条堵死——不靠「相信代码」，靠「测出来的误差只可能是 fp16 产生的」。

反证逻辑：误差量级是 dtype 的「指纹」 若真跑 fp16 ⇒ 量化误差 ~ fp16-ULP ~ 2⁻¹⁴ 量级 若静默落回 bf16 ⇒ 量化误差 ~ bf16-ULP ~ 2⁻¹¹ 量级（约大 8×） 实测 dQ/dK max_abs_err = 6.10352e-05 = 2⁻¹⁴ ， dV = 1.22e-4 = 2⁻¹³ ⇒ 正是 fp16-ULP 量级，不是 bf16 量级 ⇒ 确在跑 fp16

为什么这条值得单列： 它把「复用模板」最容易漏的失败模式（dtype 没真切、对拍假绿）变成可证伪的：误差量级对不上 fp16 就立刻露馅。实测对得上 ⇒ 放心。

「容差更紧」本身不等于「没被调来掩误差」。reviewer 在独立 build_review 上做了两个相反方向的扰动实验——放宽与收紧——来锁死这个疑点（实验后均已 revert，代码树 pristine）。

8  fp16 溢出风险：当前包络内安全

fp16 指数位少（max=65504），需确认 softmax 的 exp/LSE、大梯度不会在 I/O 边界 inf/nan。

  • 内部 exp / LSE / 归约累加全在 float（fp16 仅 I/O）——溢出只可能发生在边界 store。
  • sweep 全程 max|ref| 最高仅 ~10.9（远 ≪ 65504）；输入 O(1)，alpha=0.125。所有 softmax（指数路）配置均 PASS，无一例 fp16 溢出 FAIL。
  • reviewer 额外压测：seqlen=1024 softmax、contextual+target+window 组合 mask、determ 多 split——均无 inf/nan，误差仍 fp16-ULP 级。
诚实边界： 结论是「当前测试包络内无 fp16 已知边界」。若未来喂极端大 magnitude 输入需另测；现 contract 内无。reviewer 建议（非阻塞）可补一个极端 stress 案进一步压上界。
