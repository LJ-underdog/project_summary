M7a 不写任何新数学，也不碰 kernel / pipeline / dispatch / reference。它只在最外层边界加一条 fp16 类型轴：harness 运行时 -prec 选 fp16/bf16、fp16 入口逐字镜像 bf16、生成器多产 8 个 fp16 实例。仍 hd64、hdim_qk==hdim_v。所有引用以 git show 8b1fab06:<file> 行号为准。

读者：要 review 这次 fp16 加宽的工程师（关心「凭什么说这是零回归、且真的跑了 fp16」）
TL;DR — 一句话看懂 M7a

M7a = 纯 dtype 轴加宽。dispatch/kernel/pipeline 本就模板化于 InOutDataType，所以 fp16 只需在边界处补一条类型：example_..._bwd.cpp 据 -prec 选 fp16_t/bf16_t、新建 2 个 fp16 入口（与 bf16 入口逐字镜像,仅 bf16_t→fp16_t）、生成器多吐 8 个 batched fp16 实例。库内 4 类核心文件（kernel/pipeline/dispatch/reference）byte-identical 于 M6b。

1  总览：M7a 到底改了什么

一句话四件事——全部贴着「边界」，不进库内：

运行期选型
-prec → fp16/bf16
harness main 据 -prec 在运行期把 fp16_t/bf16_t 喂给同一套模板（example_..._bwd.cpp:1043-1062），4 处 fwd/bwd 接线各加一条 fp16 分支。
容差
fp16 elimit 更紧
get_bwd_elimit<fp16_t> 特化 rtol 5e-3/atol 1e-2（:150-154），严于 bf16 默认的 2e-2/5e-2。
复用不重写
入口逐字镜像
2 个 fp16 入口（no_group/group_backward_fp16.cpp）与 bf16 版逐字相同,仅 bf16_t→fp16_t；dispatch/kernel/pipeline 一字不改。
实例 / 构建
8 实例 + CMake glob
生成器 dtype 轴 ["bf16"]→["fp16","bf16"]（generate_instances.py:175）产 8 个 batched fp16 实例；CMake glob fp16 fwd/bwd（CMakeLists.txt:36/47）。
为什么这么轻？ 早在 M0 dispatch 签名第一个模板参数就是 InOutDataType（不是写死 bf16）。8 个里程碑全程把数据类型当模板轴携带,fp16 加宽因此退化为「在最外层多实例化一份、多接一条 runtime 分支」——这是 M0「接口先冻结」红利的兑现。

5  设计动机小结

  1. dtype 一直是模板轴,不是写死 bf16:M0 起 dispatch 第一个模板参数就是 InOutDataType,fp16 因此只需在边界多实例化、多接一条 runtime 分支,无需碰库内逻辑。
  2. 逐字镜像而非另写:fp16 入口与 bf16 入口仅差 bf16_t→fp16_t(no_group_backward_fp16.cpp:26),最大化复用、最小化新代码、天然零行为漂移。
  3. 容差按精度收紧、不放水:get_bwd_elimit<fp16_t>(:150-154)给 fp16 更严的 rtol/atol——10-bit 尾数本该过更严的关,这也成为「真跑了 fp16」的证据。
  4. 生成器优先:dtype 轴只改一行 BWD_DTYPES_M0(:174),8 个实例自动产出,实例与 dispatch 签名永不漂移。
  5. 纯 additive 构建:CMake 只追加 fp16 glob/源,既有 bf16 链接一行未删,从构建层保证 bf16 路径零扰动。
