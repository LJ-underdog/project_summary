1. 核心架构差异：单融合 kernel vs 双 kernel 拆分

这是两套实现最根本的分歧，几乎决定了后面所有差异（atomic、instance 数、perf 路径）。

💡 关键洞察：并行轴决定了要不要 atomic
单 kernel 无法同时让 dQ 的行、dK/dV 的列都"各归一个 workgroup"。我们选 KV-block 并行 → 一行 dQ 被多个 KV block 触碰 → 必须 atomic_add 或 split+reduce累加。 qianfeng用两个 kernel、各选让自己输出天然独占的并行轴 → 完全不需要 atomic，代价是 S 重算两遍 + 两次 launch。这不是谁对谁错，是"一次融合 launch 换 atomic" vs "无 atomic 换冗余计算"的取舍。

我们 单融合 MAIN

  • 一个 KV-block 并行 kernel 同时产 dV/dK（epilogue 直接写）+ dQ（float dq_acc 工作区）bwd_kernel.hpp:444-482
  • softmax 路多一个 PRE kernel 算 D=rowsum(O∘dO)bwd_kernel.hpp:1700-1754
  • POST 把 float dq_acc 转成 dQ（convert 或 reduce+convert）:1763-1792
  • MAIN 内 4 个 kernel 结构体：{batched+jagged, group} × {SiLU, softmax}
  • S=QKT 只算一次（融合内复用）

qianfeng 双 kernel 拆分

  • Kernel1 出 dQ（+softmax 的 delta）bwd_kernel_1.hpp:19-21,230
  • Kernel2 出 dK/dV，寄存器累加跨 Q 循环后一次写bwd_kernel_2.hpp:895-943
  • dispatch 同 stream 顺序 launch，delta 用 hipMallocAsync 临时 workspace 传递batched_dispatch:149-156
  • 拆分理由：dQ 行间不累加、dK/dV 列上需跨 Q 累加，两种模式不对称HSTU_BWD_DESIGN.md:51-63
  • 两个 kernel 各自重算 S（冗余 GEMM）

2. dQ 累加与确定性

我们 atomic + 可选确定性

  • 默认 atomic_add（num_splits=1）bwd_kernel.hpp:363-372
  • deterministic 模式：每个 KV-block 写独立 split slot（set，无原子）+ POST 按固定升序 reduce → 逐位可复现:1789-1792
  • kIsDeterministic 是编译期模板轴，host 端运行时 BOOL_SWITCH 选实例
  • 提供"性能(atomic) ↔ 可复现(determ)"两档给用户选

qianfeng 天然确定性（无开关）

  • bwd 源码（.hpp/.cpp/.py）grep atomic/deterministic 零命中；atomic 仅出现在设计文档HSTU_BWD_DESIGN.md:329-334（dBias 累加策略）、:350（deferred split）
  • 每个 dQ / dK / dV 输出 tile 由唯一 workgroup 负责 → 无需 atomic，天然逐位确定
  • 没有"性能 vs 复现"开关——只有一条确定性路径
  • 代价：不做 split，jagged 序列长度悬殊时负载不均（DESIGN 列为 deferred）HSTU_BWD_DESIGN.md:344-351

4. instance / build 策略

我们 精简：64 个

  • 轴：2 dtype × 2 causal × 2 softmax × 2 determ × 4 hdim = 64（仅 batched）generate_instances.py:175-198
  • 运行时 switch（零增长）：cross、jagged、window/local
  • group 直接 inline 编译，无独立 instance 文件
  • 刻意把轴推成运行时以压制膨胀

qianfeng 膨胀：192 个

  • 轴：3 mode × 2 dtype × 2 causal × 2 softmax × 2 dropout × 4 hdim = 192generate_bwd_instances.py:92-170
  • mode(batched/jagged/group) 与 dropout 都是编译期轴 → 数量大
  • cross 是运行时 switch（这点与我们一致）
  • 典型 CK instance 膨胀取向，build 体积/时间偏重

差异根源：我们把 jagged 做成运行时分支、把 group 做成独立 inline 编译的 kernel（自带 .cpp 入口、内部 BOOL_SWITCH，不计入 batched 的 64）、且无 dropout 轴，但多了 determ 轴；qianfeng 把 mode(batched/jagged/group) / dropout 做成编译期轴。window / cross 两侧都是运行时分支、对实例数差异无贡献。净结果 64 vs 192。

9. 细节展开（点击）

数学与激活路径细节

SiLU（no_softmax）路：前向 P=silu(S)·scale_p，bwd 从 Q/K 重算 S（无保存值），dS=dP·scale_p·dsilu(S)，masked-out 显式置 0。两边都用 dsilu(x)=σ(x)(1+x(1−σ(x)))。

softmax 路：前向存 LSE，bwd 用 P=exp(S−LSE) 恢复，dS=P·(dP−D)；D=rowsum(dO∘O)。我们在 PRE kernel 算 D，qianfeng 在 Kernel1 顺带算 delta 传给 Kernel2。

收尾都是 dQ、dK ×α，dV 不缩放。我们 no_softmax_pipeline.hpp:402-438 / with_softmax_pipeline.hpp:460-514；qianfeng *_dq/*_dk_dv pipeline

tile / block shape 对比（按块角色对齐）

因两边（乃至 qianfeng 两个 kernel）的 tile 序列语义/长度不同，不能按原始槽位并列，下表按「Q 块 / KV 块」角色重排。qianfeng 另按 BUILD_HSTU_FOR_GFX95 分 gfx94/gfx95 两套 preset，此处取值可能随该宏不同。

为什么 qianfeng 要重算 S 两遍

Kernel1 算 dQ=α·dS·K 需要 dS→需要 S；Kernel2 算 dK=α·dST·Q 同样需要 S。两个 kernel 各自独立、不共享中间量，所以 S=QKT 这个 GEMM 在两个 kernel 里各做一遍。我们的融合 kernel 因为 dQ/dK/dV 在同一个 kernel 内，S 算一次即被三路复用——这是"融合换省算"的直接体现，代价是引入了 dQ 的 atomic 累加。

qianfeng DESIGN.md 与实际代码的偏差
  • dropout：DESIGN 写 "deferred"，实际代码已实现（BlockDropout + 独立随机数 kernel）。
  • bias：DESIGN 列 dBias deferred；代码里 kHasBias 模板全程 plumbed，但实例生成器只出 has_bias=False → 运行时不可用。
  • 结论：读 qianfeng 要以源码为准，DESIGN 是早期规划、已被部分超越。
